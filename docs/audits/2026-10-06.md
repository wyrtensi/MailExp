## 19. Поздний ответ «Загрузить ещё» смешивает письма разных папок

**Приоритет:** P2. **Область:** frontend, бесконечная прокрутка.

**Как воспроизвести:** открыть INBOX, запросить следующую страницу и до получения ответа перейти
в Archive. Дождаться загрузки Archive, затем завершения старого запроса INBOX.

**Ожидается:** список и offset принадлежат Archive; старый ответ игнорируется.
**Фактически:** в Archive добавляются строки из INBOX, а offset/hasMore перезаписываются старым
ответом. Репродукция получила `archive-1, inbox-3, inbox-4` при выбранной папке Archive, offset 4.
Пользователь видит и может выбрать для действий письма, которые не относятся к отображаемой папке.

**Причина:** `loadMore` после `await api.getMessages` безусловно вызывает `appendMessages` и
обновляет пагинацию, не проверяя актуальность account/folder/filter. Для начальной загрузки
такой контроль уже есть; контрольный тест начальной загрузки проходит.

**Код:** [MessageList.jsx:494](https://github.com/wyrtensi/MailExpert/blob/656c861f/frontend/src/components/MessageList.jsx#L494).

**Подтверждение:** настоящий MessageList и Zustand смонтированы в React/jsdom; задерживается
обычный ответ fetch. Проверка ожидаемого списка падает из-за двух лишних ID.

## 20. Постраничный режим не позволяет получить следующую страницу поиска

**Приоритет:** P2. **Область:** frontend, поиск.

**Как воспроизвести:** выбрать постраничный режим, искать по всем папкам и получить больше
совпадений, чем `pageSize`. В тесте INBOX содержит два письма, pageSize равен 2, поиск находит
три письма в Archive.

**Ожидается:** все совпадения доступны через кнопку следующей страницы или дозагрузку поиска.
**Фактически:** доступны только первые два совпадения. «Загрузить ещё» не отображается; обе кнопки
пагинации отключены, потому что учитывают размер INBOX. Если текущая папка больше, её кнопки всё
равно загружают страницы обычного списка, а не поиска. При стандартном pageSize 50 недоступны
51-е и последующие совпадения.

**Причина:** блок дозагрузки поиска находится внутри `scrollMode === 'infinite'`. Постраничный
footer использует `messagesTotal` и `loadPage` обычной папки.

**Код:** [MessageList.jsx:4020](https://github.com/wyrtensi/MailExpert/blob/656c861f/frontend/src/components/MessageList.jsx#L4020),
[footer:4093](https://github.com/wyrtensi/MailExpert/blob/656c861f/frontend/src/components/MessageList.jsx#L4093).

**Подтверждение:** смонтированный компонент показывает два из трёх совпадений без доступной
дозагрузки. Переключение того же экземпляра в бесконечный режим даёт кнопку, запрос offset 2 и
третье совпадение. Это контроль работоспособности источника результатов и API.

## 21. Старый успешный OAuth refresh перезаписывает новое переподключение

**Приоритет:** P2. **Область:** Google и Microsoft OAuth; одна причина в двух реализациях.

**Как воспроизвести:** начать обновление токена ящика, задержать ответ провайдера, завершить
переподключение с сохранением новых credentials, затем вернуть успешный ответ старого refresh.
Для Google переподключение может переключить зарегистрированное приложение; для Microsoft —
перейти с authorization-code flow на device-code flow.

**Ожидается:** credentials последнего согласия пользователя остаются действующими; старый результат
не перезаписывает их. **Фактически:** обе реализации сохраняют результат только по ID ящика.
Google перезаписывает новый access token, оставляя новый app ID; при отсутствии refresh_token в
ответе новый refresh token сохраняется. Microsoft перезаписывает новые токены и возвращает
`oauth_public_client` из true в старое false.

**Причина:** успешные UPDATE не проверяют, что credentials/app/mode с начала запроса остались
прежними. Блокировка между refresh не сериализует этот запрос с записью OAuth reconnect.

**Код:** [googleOAuth.js:183](https://github.com/wyrtensi/MailExpert/blob/656c861f/backend/src/services/oauth/googleOAuth.js#L183),
[microsoftOAuth.js:156](https://github.com/wyrtensi/MailExpert/blob/656c861f/backend/src/services/oauth/microsoftOAuth.js#L156).

**Подтверждение:** реальные функции провайдеров, шифрование и PGlite со всеми миграциями. Commit
переподключения представлен записью соответствующих новых полей БД; callback обмена кодом не
тестировался. HTTP-ответы — управляемые fixtures. Три проверки сохранности новых credentials
падают; контроль обычного refresh без конкурентного reconnect проходит.

Google-сценарий с возвращённым старым refresh_token дополнительно показывает несовместимую пару
«новый client ID / старый refresh token». Отказ `invalid_grant` в этом сценарии задаёт HTTP fixture;
это **не** утверждение, что живой Google всегда возвращает новый refresh_token или что любое
переподключение неизбежно отключается. Само затирание свежих credentials воспроизводится и без
возврата refresh_token.

**Как воспроизвести:** сделать репетицию восстановления из снимка с hook; на исходном узле удалить

**Ожидается:** hooks соответствуют финальному снимку; прежние файлы убраны в holding directory.
Это прямо обещано [runbook](../operations/mail-node.md) в описании восстановления.
**Фактически:** старый исполняемый hook остаётся и может снова запуститься при старте mailcow.

**Причина:** `place_files` вызывает `mirror_dir` для hooks только если каталог есть в снимке.
`add_node_files` тоже копирует hooks только при наличии, поэтому полное отсутствие этого каталога
является легитимным результатом нового бэкапа.

**Код:** [node-restore.sh:199](https://github.com/wyrtensi/MailExpert/blob/656c861f/scripts/deploy/mail-node/node-restore.sh#L199),

в Git Bash. Финальный бэкап не содержит hooks, восстановление оставляет прежний исполняемый файл,

`mkdir -m`; владельцы и права Linux этой репродукцией не проверялись. Реальные файлы узла и Docker
daemon не использовались.

## 23. Отрицательное правило по телу срабатывает до загрузки тела письма

**Приоритет:** P2. **Область:** правила входящих, ленивое получение текста.

**Как воспроизвести:** создать правило «тело не содержит invoice → переместить в Processed»;
получить новое письмо, у которого `body_text` ещё NULL, или запустить правила вручную для такого
письма. Такое состояние штатное: профили провайдеров используют `fetchBody: false`.

**Ожидается:** правило, требующее незагруженного тела, пропускается. Это явно обещает подсказка
`bodyConditionNote` в обеих локалях: письмо остаётся во входящих, правила по телу не применяются
задним числом. **Фактически:** письмо перемещается из INBOX в Processed, хотя текст неизвестен.
Действие может быть и удалением в Trash; репродукция проверяла безопасное перемещение.

**Причина:** NULL заменяется пустой строкой; `not_contains` возвращает true. Предупреждение в логе
говорит, что правила не совпадут, но evaluator не пропускает зависимые от тела правила.

**Код:** [inboxRules.js:176](https://github.com/wyrtensi/MailExpert/blob/656c861f/backend/src/services/inboxRules.js#L176),
[проверка условия:121](https://github.com/wyrtensi/MailExpert/blob/656c861f/backend/src/services/inboxRules.js#L121),
[контракт UI:1058](https://github.com/wyrtensi/MailExpert/blob/656c861f/frontend/src/locales/en.json#L1058).

**Подтверждение:** настоящая `applyInboxRules`, реальные SQL и PGlite со всеми миграциями;
имитируется только внешний IMAP move. При NULL получено `folder=Processed, uid=42` и один move.
Контроли: загруженный текст с invoice остаётся во входящих; загруженный текст без него перемещается.
Тест не утверждает, что прочитал неизвестное тело: ошибка состоит в действии до получения текста.

## 25. Редактирование отложенной пересылки теряет уже сохранённое вложение

**Приоритет:** P2. **Область:** отложенная отправка, пересылка с вложениями.

**Как воспроизвести:** запланировать пересылку с вложением, окончательно удалить исходное письмо,
открыть «Редактировать» у отложенной пересылки, изменить тему и снова запланировать её.

**Ожидается:** вложение берётся из содержимого, уже сохранённого в долговечной очереди.
**Фактически:** редактирование отвечает 200, отменяет старое задание и удаляет его содержимое.
Возвращаются только ссылки на исходное письмо; повторная отправка отвечает 404
`Forwarded message not found`. Пересылку нельзя отправить с прежним вложением через этот редактор;
удаление проблемного вложения позволит отправить только оставшуюся часть письма.

**Причина:** начальный send разрешает ссылки и сохраняет байты вложений в `outgoing_messages.mail`,
но `restoredCompose` восстанавливает только индексы `stored.uploads`, исключающие пересылаемые
вложения. Старый blob удаляется при отмене, а ссылки повторно разрешаются на следующем send.

**Код:** [sendQueue.js:310](https://github.com/wyrtensi/MailExpert/blob/656c861f/backend/src/services/sendQueue.js#L310),
[удаление blob:282](https://github.com/wyrtensi/MailExpert/blob/656c861f/backend/src/services/sendQueue.js#L282),
[индексы uploads:377](https://github.com/wyrtensi/MailExpert/blob/656c861f/backend/src/routes/send.js#L377).

**Подтверждение:** настоящие send/scheduled routes, очередь и PGlite со всеми миграциями. До Edit
проверены 23 байта вложения в blob; после Edit uploads пусты, blob удалён, resend отвечает 404.
Контроли: без Edit пересылка успешно использует сохранённые байты после удаления исходной строки;
Edit с существующим оригиналом даёт успешный resend. Удаление представлено DELETE строки БД,
загрузка вложения и SMTP — fixtures; живой IMAP purge, браузер и SMTP не запускались.

## 26. Некорректный внутренний HTTP-запрос завершает tenant-worker

**Приоритет:** P2. **Область:** доступность внутреннего tenant-worker.

**Как воспроизвести:** отправить непосредственно HTTP-серверу worker запрос с request-target,
который HTTP parser принимает, но `new URL` не может разобрать. Синтетическая репродукция сохранена
в `deploy/worker-url-crash.mjs` в каталоге материалов аудита.

**Ожидается:** один неверный запрос получает отказ, процесс продолжает обслуживать остальные.
**Фактически:** async handler отклоняет promise до проверки токена; HTTP callback не обрабатывает
это отклонение, Node завершает процесс с exit 1 и `ERR_INVALID_URL`.

**Причина:** `new URL(req.url, 'http://worker')` находится перед `try`; production wrapper вызывает
handler без обработки его promise. Обработка ошибок внутри handler этот случай не покрывает.

**Код:** [server.mjs:272](https://github.com/wyrtensi/MailExpert/blob/656c861f/deploy/tenant-worker/server.mjs#L272),
[HTTP callback:372](https://github.com/wyrtensi/MailExpert/blob/656c861f/deploy/tenant-worker/server.mjs#L372).

**Подтверждение и пределы:** настоящая `createHandler`, такой же wrapper и реальный TCP-запрос
к дочернему процессу на loopback. До неверного запроса `/health` отвечает 200, обычный запрос без
токена — 401; после него процесс завершается. Fixture использует синтетический token и не запускает
PowerShell, не читает сертификаты. Выполнено на Node 24; Node 22 отдельно не запускался.

Worker не публикует host port: нужен прямой доступ из внутренней сети контейнеров. Обычные запросы
панели используют фиксированные paths и не воспроизводят дефект. Compose `restart: unless-stopped`
обеспечивает перезапуск; постоянная остановка и доступность этого пути из интернета не заявляются.
Фактическое поведение Docker restart и активных EXO operations в этой репродукции не проверялось.

## 27. Отправка во время сохранения оставляет лишний черновик

**Приоритет:** P2. **Область:** редактор письма, конкурентные Save draft и Send.

**Как воспроизвести:** начать сохранение нового черновика; пока ответ с UID ещё не получен,
нажать Send. Дождаться успешного принятия отправки, закрытия редактора и позднего ответа сохранения.
Такой порядок возможен после APPEND на сервере, пока HTTP-ответ сохранения находится в пути.

**Ожидается:** сохранённый экземпляр удаляется, как при обычном Send после завершившегося Save.
**Фактически:** Send доступен во время сохранения, письмо принимается очередью, редактор закрывается;
после позднего ответа черновик остаётся. Запрос DELETE для нового UID не выполняется.

**Причина:** `handleSend` проверяет `sending`, но не незавершённое сохранение; его closure ещё
не имеет draftUid. Очистка пропускается, а поздний `setDraftUid` в размонтированном редакторе
не запускает удаление. Это не прежние ошибки baseline сохранения или FIFO открытия редакторов.

**Код:** [ComposeModal.jsx:861](https://github.com/wyrtensi/MailExpert/blob/656c861f/frontend/src/components/ComposeModal.jsx#L861),
[очистка:933](https://github.com/wyrtensi/MailExpert/blob/656c861f/frontend/src/components/ComposeModal.jsx#L933),
[поздний UID:1048](https://github.com/wyrtensi/MailExpert/blob/656c861f/frontend/src/components/ComposeModal.jsx#L1048).

**Подтверждение:** настоящий ComposeModal и Zustand в React/jsdom, условный host соответствует
`composing && <ComposeModal />` в MailApp. HTTP fixture моделирует сохранение UID 9 и задержку
ответа. При Send во время задержки DELETE отсутствует; контроль Save-before-Send вызывает
`DELETE /mail/draft/9`. Репродукция подтверждает отсутствие очистки после принятия письма очередью,
а не живую доставку или автоматическую повторную отправку. IMAP persistence представлен fixture;
JSX/Vite-env и i18n адаптеры повторяют подход существующих render tests, обработчики не заменены.

## Кандидаты, не включённые в подтверждённые баги

- **Access sync при смене настроек во время запроса.** CLI действительно может сохранить новые
  настройки, пока начатый прогон работает со старым snapshot и отключает пользователей. PGlite
  подтверждает поведение. Однако документация не обещает отмену начатого прогона; защита baseline
  относится к сохранению состояния и последующим прогонам. Для признания этого багом сначала
  нужно определить ожидаемое поведение, поэтому отмена не выдумана как существующее требование.
- **Trace более десяти получателей.** Ограничение детальных запросов явно записано в спецификации;
  это не новый баг.
- **Restore с переименованным/внешним томом БД из compose.local.yml.** Fixture подтверждает обход
  стандартной проверки свежести и замену ключей до ошибки pg_restore. Но операторская документация
  прямо предупреждает, что изменение томов БД ломает предпроверки; это уже описанное ограничение.
  Перезапись существующей БД не заявляется: pg_restore использует одну транзакцию и не имеет --clean.

Новые репродукции не заменяют ранее исправленные проблемы и не меняют принятых архитектурных решений.
