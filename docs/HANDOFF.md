# MailExpert: передача проекта

Документ для человека, который принимает проект: что это, как устроено, что готово, что нет и что
нужно, чтобы доделать. Простыми словами, без деталей реализации; ссылки ведут туда, где подробно.

Состояние на 2026-10-05, версия `main` — `9a75886d` (она же в канале `latest`).

Сетевые требования всех модулей — [карта портов](operations/ports.md): direct-вход TCP 80/443
и необязательный UDP 443, Cloudflare Tunnel — исходящий TCP/UDP 7844, внутренний frontend —
loopback 8080. Базы и tenant-worker не публикуются; почтовый узел принимает 25 только от EOP,
587/993 только от панели, API использует 443. В карте отдельно указаны DNS, SSH, исходящие
интеграции, dev/HTTPS и стенды `me-stage` / `mxu`; это справочник для передачи сетевых правил.

## 1. Что это в двух словах

MailExpert — веб-почта для команды, которая работает с общими почтовыми ящиками. Открываешь сайт
панели, входишь через Google или Cloudflare и видишь все ящики компании: читаешь, отвечаешь,
пересылаешь, раскладываешь письма. Это форк открытого проекта
[MailFlow](https://github.com/maathimself/mailflow) (лицензия AGPL-3.0).

Главная идея: **ящики принадлежат установке, а не человеку.** Сервер сам держит все ящики
подключёнными круглосуточно, даже когда никто не вошёл. Сотрудник не подключает ящик к себе — он
просто входит и работает. Прав «этот ящик видит только Петя» нет: все вошедшие видят все ящики.
Кто что сделал, записывается в журнал.

## 2. Как это работает для людей

**Роли.** Две: сотрудник и администратор.

- **Сотрудник** работает с почтой: читает, пишет, отвечает, откладывает письма, отправляет позже,
  ищет, ведёт контакты, настраивает правила разбора входящих (правила общие и видны всем). Может
  подключить Gmail через Google, создать ящик на своём домене, сразу удалить обычный ящик, а для
  ящика на своём домене — запросить удаление (с причиной, ящик удаляется через несколько дней).
- **Администратор** настраивает всё остальное: пользователей, ящики по IMAP/SMTP вручную и их
  настройки подключения (сервер, логин), ящики Microsoft 365 (подключение и переподключение),
  интеграции, почтовый узел, тенант Microsoft, плагины (включает для всех сразу), обновление
  панели. Сотрудники настройки сервера не трогают.

**Вход.** Через Google или Cloudflare Access; пускает только одобренных пользователей из списка.
Вход по паролю — только на тестовых стендах.

**Ящики подключаются сами.** Gmail — через Google OAuth (без паролей приложений), Microsoft 365 —
через OAuth Microsoft, любые другие — по IMAP/SMTP, ящики на своих доменах — через почтовый узел
(раздел 5). Если ящик отвалился, панель показывает его состояние; переподключение Microsoft делает
только администратор.

**Журнал.** Кто открыл, отправил, переместил, удалил, кто поменял правило, пользователя, настройки
узла, кто обновил панель — всё в журнале у администратора.

**Что ещё есть внутри:**

- отмена отправки (5 секунд) и «отправить позже» — через надёжную очередь заданий, переживающую
  перезапуск сервера;
- статус доставки письма и отбивки (для ящиков узла);
- безопасный просмотр писем из «Спама» и объяснение «почему письмо в Спаме»;
- переписка Gmail собирается в цепочки так же, как в самом Gmail;
- плагины, в комплекте GTD;
- демо-режим без настоящей почты (для показа).

Полное описание каждого экрана — [руководство пользователя](user-guide/README.md).

## 3. Из чего состоит проект

Проект — это несколько программ (модулей), каждая в своём контейнере Docker.

| Модуль | Что делает простыми словами | Обязательный? |
|---|---|---|
| **frontend** | сам сайт: страницы, которые видит человек в браузере | да |
| **backend** | «мозг»: держит связь со всеми ящиками, синхронизирует почту, отправляет письма, хранит настройки, отвечает сайту. Работает одним процессом | да |
| **postgres** | база данных: пользователи, ящики, копии писем, журнал, зашифрованные пароли и токены | да |
| **redis** | быстрая память для сессий входа | да |
| **edge** (Caddy и/или cloudflared) | «входная дверь» из интернета: шифрование HTTPS или туннель Cloudflare | да |
| **tenant-worker** | помощник для работы с тенантом Microsoft (настройка EOP, карантин, трассировка писем) | только если нужен EOP |
| **почтовый узел** (mailcow) | свой почтовый сервер для ящиков на своих доменах, почта идёт через Microsoft EOP | только если нужны свои домены |
| **таймеры на сервере** | ночной бэкап, проверка здоровья, исполнитель обновлений из панели | да (ставятся сами) |

Снаружи проект зависит от: Cloudflare (DNS, туннель, вход), Google (вход и подключение Gmail),
тенанта Microsoft (только для EOP), S3-хранилища у другого провайдера (бэкапы),
Healthchecks.io (оповещения в Telegram).

Как они связаны:

```text
Браузер сотрудника
    |  HTTPS
    v
edge (Caddy или туннель Cloudflare)
    v
frontend ──> backend ──> postgres, redis
               |
               ├──> Gmail, Microsoft 365, другие почтовые серверы (IMAP/SMTP, OAuth)
               ├──> почтовый узел mailcow (API, IMAP, SMTP)   [если есть]
               └──> tenant-worker ──> Microsoft Graph и Exchange Online   [если есть]

Почта своих доменов:  интернет <──> Microsoft EOP <──порт 25──> почтовый узел
```

Подробная таблица модулей, портов и связей —
[deployment-system.md, разделы 1–2](architecture/deployment-system.md).

## 4. Что можно разносить по серверам

Коротко: **панель — один сервер, почтовый узел — второй, отдельный.** Больше разносить нельзя.

| Что | Где живёт |
|---|---|
| frontend, backend, postgres, redis, edge, tenant-worker | все вместе на одном сервере панели |
| почтовый узел (mailcow) | всегда на своём отдельном сервере, один узел на одну панель |
| бэкапы | хранилище S3 у третьего провайдера (не там, где серверы) |

Не поддерживается сейчас (и почему, коротко):

- узел на одном сервере с панелью — обоим нужен порт 443, проксирование не сделано;
- внешняя или облачная PostgreSQL — бэкап, обновление и откат работают внутри своего контейнера базы;
- несколько копий backend — он держит соединения с ящиками в памяти одного процесса;
- несколько узлов на одну панель — настройки узла рассчитаны на один;
- tenant-worker на другом сервере — связь с ним без шифрования, только внутри одного сервера;
- отказоустойчивость — сервер панели один, переезд плановый, с простоем.

Подробно — [deployment-system.md, раздел 3](architecture/deployment-system.md).

**Варианты установки:**

| Вариант | Серверы | Когда |
|---|---|---|
| **A. Панель + узел** | два сервера Ubuntu 24.04, по 4 ядра и 8 ГБ памяти | нужны ящики на своих доменах через EOP |
| **B. Только панель** | один сервер Ubuntu 24.04, минимум 2 ядра, 4 ГБ, 20 ГБ диска | только Gmail и внешние ящики |
| **C. Стенд** | один сервер или Docker на своей машине | проверить версию перед продом |

Для сервера узла провайдер должен разрешать порт 25 в обе стороны, давать статический IPv4 и
настройку PTR, IP не должен быть в чёрных списках.

## 5. Что готово, а что нет

### Gmail и обычные ящики — готово

Код готов и проверен тестами и на стенде: подключение Gmail через Google OAuth (несколько
приложений Google), обновление токенов, состояние «нужно переподключить», цепочки писем как в
Gmail, поиск и фильтр ящиков по состоянию, плавное подключение большого числа ящиков после
перезапуска. Обычные IMAP/SMTP-ящики работают так же.

Чего не было (нужен реальный сервер и реальные ящики, кодом это не закрыть):

- живой цикл OAuth на настоящих Gmail: подключение, истечение токена, отзыв доступа, повторное
  подключение;
- подключение волнами 10 → 25 → 50 → 100 ящиков с замером памяти, процессора и ошибок Google;
- сутки непрерывной работы, перезапуск и восстановление из бэкапа на целевом сервере.

На стенде прогнан сценарий нагрузки: десять сотрудников в общих ящиках, 200 ящиков и 60 000 писем,
ни одно не потеряно и не задвоено.

Важно для 100 ящиков: непроверенное Google-приложение пускает не больше 100 уникальных
пользователей за всю жизнь, и счётчик не уменьшается. Поэтому панель умеет работать с несколькими
Google-приложениями и раскладывает ящики по ним; другой путь — пройти проверку Google (OAuth
verification). Подробно — [operations/google-oauth.md](operations/google-oauth.md).

### Развёртывание и обновление — готово, кроме проверки на живом сервере

Готово: установка одной командой (`install.sh`), предпроверка (`status.sh`), обновление по SSH
(`update.sh`) и **кнопкой из панели**, откат (`rollback.sh`), ночные бэкапы панели и узла,
проверка здоровья, CLI для администратора (`mailexpert`), установка с помощью ИИ-агента.

Проверено на стенде: установка, обновление кнопкой из панели, откат, отказ ставить откатанную
версию повторно.

Не проверено на настоящем сервере с systemd: таймеры исполнителя обновлений, `rollback.sh`, бэкап
и восстановление почтового узла, обёртка CLI на хосте. Стенд работает в Docker без systemd, поэтому
там эти части запускались обходным путём.

Не проводилась боевая приёмка: полная репетиция переезда панели между двумя серверами по
инструкции с замером простоя ([deployment.md, раздел 8](operations/deployment.md)).

Перед первым боевым запуском (любым, не только с EOP) проверить: настройку `TRUST_PROXY` за
Cloudflare ([deployment.md](operations/deployment.md)) и, если подключаются ящики Microsoft 365,
реальные поля токена Microsoft при подключении.

Не настроено: правило в GitHub, которое запрещает двигать тег `latest` кому-то кроме CI и
владельца (Settings → Rules → Rulesets, [operations/README.md, раздел 9](operations/README.md)).

### Свои домены через Microsoft EOP — код написан, не проверен с настоящим Microsoft

Что сделано (этапы 0–7): почтовый узел mailcow управляется из панели — домены, ящики, квоты,
очередь, журнал Postfix, карантин, статус доставки, проверки DNS, окна простоя узла. Драйвер
тенанта Microsoft (через tenant-worker) умеет заводить домены в тенанте, коннекторы, зеркало
получателей (DBEB), антиспам-политику, трассировку писем и выпуск из карантина EOP.

Всё это проверено только против **поддельного EOP** на стенде и по документации Microsoft.
Настоящего тенанта у проекта не было, и первый узел mailcow на настоящий сервер не ставился.
Поэтому часть допущений о том, как именно отвечает Microsoft, не подтверждена.

**Что нужно, чтобы доделать (этап 8):**

1. Тенант Microsoft — платный или пробный, с подпиской Exchange Online Protection (в бесплатном
   developer-тенанте E5 нельзя создать входящий коннектор).
2. Пробный домен второго уровня, который не жалко.
3. Сервер для узла (требования — раздел 4), на нём mailcow по
   [mail-node.md](operations/mail-node.md).
4. Приложение в Microsoft Entra с сертификатом для tenant-worker
   ([mail-node.md, раздел 6е](operations/mail-node.md)).
5. Пройти ручные эксперименты из
   [eop-panel-requirements.md, раздел 6](architecture/mail-node-research/eop-panel-requirements.md).
   Главные: письмо уходит наружу и приходит через EOP; отбивки доходят; минимальные права
   исполнителя в Exchange (№16); выпуск письма из карантина (№17); запись антиспам-политики
   (№25); зеркало получателей DBEB (№8); трассировка (№15, №24). Ответы Microsoft сохраняются как
   образцы для тестов, код правится там, где Microsoft ответил не так, как ожидалось.

На первом настоящем узле также пройти чек-лист
[mail-node.md, раздел 9](operations/mail-node.md) («Проверить на первом узле»): доставка через EOP,
настоящий сертификат, пинги диска, белый список fail2ban, файрвол узла. После обновления панели,
которое меняет правило раскладки спама, применить его на узле заново (панель об этом предупреждает).

## 6. Как поставить и обновить

- Быстрый старт — [operations/quickstart.md](operations/quickstart.md) (в том числе как
  поставить с помощью ИИ-агента).
- Полная инструкция оператора — [operations/README.md](operations/README.md): подготовка,
  установка панели и узла, тенант, бэкапы, мониторинг, обновление, откат, переезд, неполадки.
- Команды администратора — [operations/cli.md](operations/cli.md).

Как устроены версии: каждая сборка с зелёного `main` получает тег `sha-<12 символов коммита>`.
Когда сборка готова к проду, владелец запускает workflow `promote.yml`, и она становится `latest`.
Панель предлагает обновиться только до `latest`, только вперёд и только после подтверждения
администратора; перед обновлением делается бэкап базы.

- Что ещё перенести из MailFlow (на выбор владельца): исправление Yahoo, кнопка «Done» в GTD,
