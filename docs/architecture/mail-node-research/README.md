# Почтовый узел за Microsoft EOP и сервер для панели: исследование

> Статус: исследование от 2026-09-21, раздел 2 ниже дополнен и местами исправлен [ревизией EOP + mailcow от 2026-09-28](eop-review.md). Это рекомендации и расчёты, решения по ним принимает владелец (см. «Открытые решения»). Подробные отчёты с источниками лежат рядом: [платформы](platforms.md), [EOP и хостинг](eop-and-hosting.md), [ревизия EOP + mailcow](eop-review.md), [замер памяти и базы](benchmark.md), скрипты замера — в [`bench/`](bench/).

## Зачем

MailExpert должен заводить ящики на собственных доменах. Требования владельца:
- ящик заводит любой вошедший пользователь, выбирая домен из списка;
- удаление ящика в MailExpert только отключает его на почтовом сервере;
- повторное создание того же адреса включает ящик обратно;
- своей почтовой платформы не пишем, берём готовую сборку Postfix/Dovecot с API;
- входящая и исходящая почта идёт через Microsoft EOP;
- до 500 ящиков, рабочий сервис для многих сотрудников.

Исследование отвечает на пять вопросов: какую платформу взять, что нужно от EOP, какой сервер нужен панели и почтовому узлу (вместе и раздельно), как сэкономить ресурсы и нужна ли другая база данных.

## Итог

- **Платформа почтового узла — mailcow-dockerized** с выключенным антивирусом. Запасной вариант — Stalwart, после выхода версии 1.0.
- **Раскладка по серверам.** Рекомендуется два сервера:
  - панель — 4 vCPU / 8 ГБ на обычном VPS;
  - почтовый узел — 4 vCPU / 8 ГБ, NVMe, провайдер с портом 25 и PTR.

  Один сервер на 4 vCPU / 8 ГБ подходит и для 500 ящиков, если Dovecot настроен по [mail-node.md](../../operations/mail-node.md) (раздел 3, шаг 4). В нагрузочном тесте mailcow и панель вместе заняли в пике 3,7 ГБ, а при заводе 100 тысяч старых писем — 5,6 ГБ (раздел 4.3). 16 ГБ — если база панели большая. Проверено и на стенде, ограниченном как такой сервер (4 vCPU с
  урезанной частотой, 8 ГБ): 500 ящиков узла, 125 Gmail и 125 тысяч писем работают без OOM и почти без
  swap, пики на 4 ядрах длиннее ([mail-node.md](../../operations/mail-node.md), раздел 6а).
- **Главная статья расходов — лицензии EOP**, а не серверы. Ориентир $1-2 за ящик в месяц, то есть порядка $500-1000 в месяц на 500 ящиков. Официального прайса нет, цену нужно запрашивать у партнёра Microsoft.
- **Квоты — адаптивные.** Ящик стартует с 300-500 МБ, а MailExpert расширяет квоту по мере заполнения. Квота место на диске не резервирует, диск считается по реальному объёму почты.
- **База панели остаётся на PostgreSQL**, её нужно настроить: сейчас она работает на заводских параметрах.

## 1. Платформа почтового узла

Подробно — [platforms.md](platforms.md).

| Платформа | Итог | Почему |
|---|---|---|
| **mailcow-dockerized** | **рекомендация** | подробности ниже таблицы |
| Stalwart (Community) | запасной вариант | один бинарник на Rust, 2-4 ГБ. Но у аккаунта нет флага «отключён»; нельзя предъявить EOP клиентский сертификат при отправке, значит коннектор возможен только по IP; до версии 1.0 (ожидается около октября 2026) API ломали. Пересмотреть после 1.0 |
| Mailu | третий | лёгкий (1 ГБ без антивируса), но relayhost только один на все домены; мажорного релиза не было с 2024.06; в 2026 была уязвимость в API с оценкой CVSS 7.5 |
| docker-mailserver, Mox | отпали | нет стабильного API для управления ящиками |
| iRedMail | отпал | API только в платной версии |
| Carbonio, Zimbra | отпали | от 16 ГБ, собственный тяжёлый стек |
| Poste.io | отпал | закрытый код, лицензия запрещает обслуживать третьих лиц |

**Почему mailcow:**
- **API покрывает весь жизненный цикл ящика:** создание, отключение (`active: 0`), включение обратно с новым паролем, список доменов, DKIM.
- **Связка с EOP настраивается через тот же API:** relayhost на каждый домен, обязательный TLS к EOP
  через TLS Policy Map (DANE по умолчанию EOP не проверяет). Заводить диапазоны EOP как «forwarding
  host» в mailcow не нужно: они уже есть в собственном белом списке mailcow, а файрвол узла и так
  пускает порт 25 только с диапазонов EOP — подробности [в ревизии](eop-review.md), находки 1 и 13.
- **Postfix уже предъявляет свой сертификат,** поэтому возможен коннектор EOP по сертификату. Microsoft рекомендует именно его: только через такой коннектор уходят наружу отказы о недоставке и пересылки.

Облегчённых форков mailcow, которые кто-то сопровождает, нет.

**Семантика отключения в mailcow:**
- `active: 0` — входящая почта отклоняется как для несуществующего получателя, вход запрещён. Процессор и память ящик не тратит, остаётся только место на диске под уже полученные письма. Это и есть «удаление = отключение» из требований.
- `active: 2` — вход запрещён, но почта продолжает приходить.

«Повторное создание» MailExpert выполняет так: ищет ящик, и если он есть — включает его и задаёт новый пароль, иначе создаёт.

**Условия эксплуатации mailcow:**
- Облегчение: `SKIP_CLAMD=y` (антивирус делает EOP, экономия 1.5-3 ГБ), `SKIP_OLEFY=y`, `SKIP_FTS=y` — MailExpert ищет в своей базе. SOGo не отключать: отключение помечено как неподдерживаемое, а без пользователей SOGo занимает около 240 МБ (замер). Главная экономия — настройки Dovecot, раздел 5.
- Админку и API не открывать в интернет. API разрешить только для IP панели (`API_ALLOW_FROM`). В 2025-2026 в PHP-админке закрыли несколько серьёзных уязвимостей, в том числе с оценкой 9.1.
- IP панели внести в белый список блокировок mailcow. Панель ходит ко всем ящикам с одного адреса, и блокировка за неудачные входы одного ящика отрезала бы все.
- Обновляться в течение нескольких дней после релиза. Релизы выходят раз в 1-2 месяца.

## 2. Microsoft EOP

Подробно — [eop-and-hosting.md](eop-and-hosting.md).

- **Продукт.** Продаётся под названием «Built-in security add-on for on-premises mailboxes», это бывший EOP standalone. Работает с любым SMTP-сервером, не только с Exchange.
- **Лицензии.** Нужна лицензия на каждый ящик, ориентир $1-2 в месяц, продаётся через партнёров. Для пилота запросить цену и минимальный объём.
- **Коннекторы:**
  - входящий (EOP → узел) — на имя узла, а не на IP;
  - исходящий (узел → EOP) — по сертификату, а не по IP.

  Тогда смена IP узла не требует менять коннекторы.
- **Лимит внешних получателей в сутки на весь тенант** (введён в 2025) распространяется и на почту, релеенную с нашего узла. Для 500 лицензий расчётно около 46 500 в сутки. Это вывод, а не цифра Microsoft; кроме того, Microsoft меняет формулу с 2026-09-14, поэтому проверять в отчёте EAC. Применяется ли ещё лимит 10 000 получателей в сутки на ящик к такой схеме, Microsoft прямо не пишет — уточнить у поддержки.
- **Домены.** Начинать с режима Internal Relay: неизвестных получателей отклоняет Postfix узла. Это
  не безобидный периметр — EOP уже принял письмо от внешнего отправителя (`250 OK`) до того, как
  Postfix его отклонит, поэтому отказ на узле оборачивается NDR-бэкскаттером от EOP на (часто
  поддельный) адрес исходного отправителя. Режим Authoritative с блокировкой несуществующих адресов
  на стороне Microsoft (DBEB) устраняет это структурно, но требует завести каждый ящик получателем
  в тенанте (каталога для автосинхронизации нет, интеграция — только программно через EXO
  PowerShell) и лицензии EOP на каждого такого получателя. Это больше не «можно сделать позже» —
  разбор рисков и порядок перехода Internal Relay → Authoritative — [в ревизии](eop-review.md),
  находки 8 и 9.
- **DNS:**
  - MX указывает на EOP;
  - SPF включает EOP;
  - DKIM: mailcow создаёт ключ на каждый домен автоматически, подпись начинается сама — запись
    в DNS нужно публиковать сразу, не оставлять ключ без неё. Подписывать может и EOP, и mailcow
    одновременно — двойная подпись не ошибка, вопрос лишь в том, кто именно подписывает и подтверждено
    ли, что EOP подписывает коннекторный relay — [в ревизии](eop-review.md), находка 3;
  - DMARC обычный;
  - PTR узла для доставки не критичен, потому что вся исходящая почта идёт через EOP, но нужен провайдеру и для порядка.
- **Файрвол узла.** Входящий порт 25 открыт только для диапазонов EOP. Список меняется, его лучше обновлять из веб-сервиса Microsoft, а не держать в конфиге руками.
- **Общий коннектор — общая точка отказа.** Все домены и ящики узла используют один исходящий
  коннектор; при признаках компрометации (например, всплеск рассылки с одного ящика) EOP блокирует
  коннектор целиком для всех клиентов сразу, до снятия блокировки вручную. Лимиты отправки на домен/
  ящик в mailcow не выставлены по умолчанию — [в ревизии](eop-review.md), находка 7.

**Смена IP почтового узла.** MX указывает на EOP, а исходящая почта уходит через EOP, поэтому IP узла снаружи не виден, и репутацию нового IP «прогревать» не нужно. Смена IP сводится к списку:
1. Поменять A-запись имени узла. TTL заранее держать около 300 секунд.
2. Настроить PTR у нового провайдера.
3. Убедиться, что у нового провайдера открыт порт 25.
4. Проверить, что оба коннектора настроены по имени и по сертификату.

Со стороны панели ничего не меняется: правила доступа на узле привязаны к IP панели.

## 3. Замеры

Подробно, с методикой и конфигами — [benchmark.md](benchmark.md).

- **Стенд:** Dovecot 2.3.21 (та же ветка, что в mailcow) и клиент на ImapFlow 2.0.3 с опциями MailExpert, TLS, в Linux-контейнерах.

| Ящиков в IDLE | Клиент (Node) | Dovecot |
|---|---|---|
| 0 | 69 МБ | 5 МБ |
| 100 | 78 МБ | 203 МБ |
| 250 | 99 МБ | 499 МБ |
| 500 | 118 МБ | 990 МБ |

- **На одно постоянное соединение:** около 100 КБ в панели и около 2 МБ на почтовом сервере. Эти 2 МБ складываются из процесса `imap` и TLS-посредника `imap-login`, в каком соотношении — не измерено. Рост линейный, ошибок подключения не было.
- **Замер в mailcow под панелью (2026-09-24)** — [mail-node.md, раздел 6а](../../operations/mail-node.md). На 500 ящиках сессий вдвое больше (IDLE и синхронизация), а сессия в mailcow дороже, около 3,9 МБ: Dovecot занимает 3,9 ГБ. С настройками Dovecot из раздела 5 — около 0,5 ГБ в обычной работе и 2,2 ГБ в пике. Остальной mailcow — около 1 ГБ, от числа ящиков почти не зависит.
- **Процессор в простое** почти не нагружен. Узкое место почтового сервера — диск.
- **Письмо в базе панели** с кэшированным телом занимает около 10.8 КБ (синтетика):
  - 6.8 КБ — строка и TOAST, из них около 5.3 КБ — сжатые тела;
  - 4 КБ — индексы, из них 71% — пять GIN-индексов поиска.
- **Вложения** панель на диске не хранит, они подгружаются с почтового сервера при открытии.
- **Не измерено:** всплески синхронизации, живая нагрузка сотрудников, вложения, Gmail. Это закрывает нагрузочный тест волнами 10 → 25 → 50 → 100 из roadmap.
- **Настройка MailExpert по умолчанию:** `IMAP_MAX_PERSISTENT_PER_HOST` не задан, поэтому все ящики одного сервера держат постоянное соединение.

## 4. Серверы

### 4.1 Панель отдельно (500 ящиков)

| Компонент | Память |
|---|---|
| Node: соединения с 500 ящиками (замер) | ~120 МБ |
| Node: API, WebSocket сотрудников, фоновые задачи, всплески синхронизации (оценка) | 0.2-1.4 ГБ |
| PostgreSQL (замер до 100 тысяч писем — до 0,95 ГБ; дальше растёт с базой) | 1-4 ГБ |
| Redis, Caddy, фронтенд | ~0.1 ГБ |
| ОС и Docker | ~0.5 ГБ |

Открытая вкладка сотрудника — одно WebSocket-соединение на десятки килобайт. Нагрузка от сотрудников идёт в процессор и базу, а не в память Node.

| Писем в кэше на ящик | База на 500 ящиков |
|---|---|
| 2 000 | ~11 ГБ |
| 5 000 | ~27 ГБ |
| 10 000 | ~54 ГБ |

- **Минимум:** 2 vCPU / 4 ГБ / NVMe 80-100 ГБ.
- **Рекомендуется:** 4 vCPU / 8 ГБ / NVMe 100-200 ГБ.
- **16 ГБ** — если база больше ~50-100 ГБ.

Порт 25 панели не нужен.

### 4.2 Почтовый узел отдельно

- **Память на 500 ящиков (замер под панелью):** Dovecot с настройками из раздела 5 — около 0,5 ГБ, в пике 2,2 ГБ (без них 3,9 ГБ). Остальной mailcow — около 1 ГБ: SOGo, Postfix, MariaDB, Rspamd, служебные контейнеры. mailcow целиком в пике — 3,3 ГБ. Всё, что остаётся, уходит под файловый кэш.
- **Рекомендуется:** 4 vCPU / 8 ГБ + swap, NVMe в RAID1. 16 ГБ — если почты много и нужен больший файловый кэш.
- **Диск — по реальному объёму почты**, потому что квота место не резервирует:

| Среднее реальное заполнение ящика | Почта 500 ящиков | + запас 20% |
|---|---|---|
| 200 МБ | 100 ГБ | ~120 ГБ |
| 500 МБ | 250 ГБ | ~300 ГБ |
| 1 ГБ | 500 ГБ | ~600 ГБ |

Бэкапы держать у другого провайдера, по объёму не меньше живых данных плюс инкременты. В mailcow для этого есть скрипт `helper-scripts/backup_and_restore.sh`.

**Провайдеры с портом 25:**
- Netcup и Contabo обычно не блокируют его;
- Scaleway снимает блокировку самостоятельно через настройки;
- Hetzner и OVH — по заявке, у Hetzner не раньше месяца жизни аккаунта;
- DigitalOcean не подходит.

Цены в [eop-and-hosting.md](eop-and-hosting.md) индикативные, у ряда провайдеров они менялись в 2026.

### 4.3 Один сервер на всё

500 ящиков, Dovecot настроен по [mail-node.md](../../operations/mail-node.md) (раздел 3, шаг 4). Диапазоны — от обычной работы до пика, когда письмо приходит сразу во все ящики.

| Компонент | 8 ГБ | 16 ГБ |
|---|---|---|
| Dovecot (замер; до 3 при заводе старой почты) | 0.5-2.2 | 0.5-2.2 |
| Остальной mailcow (замер) | 1-1.4 | 1-1.4 |
| Node панели (замер в нагрузочном тесте с поиском) | 0.1-0.35 | 0.1-0.35 |
| PostgreSQL панели (замер до 100 тысяч писем; для 16 ГБ — оценка под большую базу) | 0.2-1 | 3-4 |
| Redis, Caddy, фронтенд | 0.1 | 0.1 |
| ОС и Docker | 0.6 | 0.6 |
| **Занято, ГБ** | **2.5-5.7** | **5.3-8.7** |
| **Под файловый кэш, ГБ** | **2.3-5.5** | **7.3-10.7** |

Худший случай в замере — завод 100 тысяч старых писем в Dovecot и их синхронизация панелью: всё вместе 5,6 ГБ плюс ОС. Поиск по всем ящикам на 100 тысячах писем — от 8 мс до 0,6 с, после миграции 0072 ([mail-node.md](../../operations/mail-node.md), раздел 6а).

- **8 ГБ** — рабочий вариант на 500 ящиков с настройками Dovecot. Без них Dovecot один занимает 3,9 ГБ, и 8 ГБ хватает только примерно на 250 ящиков.
- **16 ГБ** — если база панели большая и PostgreSQL нужен кэш. Если бюджет позволяет, лучше 6-8 ядер.

Что нужно решить при совмещении:
1. mailcow занимает порты 80/443, как и Caddy. Решение — `HTTP_BIND=127.0.0.1`, `HTTP_PORT=8080`, `HTTPS_BIND=127.0.0.1`, `HTTPS_PORT=8443` (штатная схема mailcow за reverse proxy, Caddy в списке поддерживаемых). Заодно админка mailcow перестаёт быть видна из интернета.
2. Сертификат для Postfix и Dovecot (EOP требует сертификат от публичного CA) выпускает Caddy. Post-hook копирует его в `data/assets/ssl/` и перезапускает Postfix и Dovecot.
3. Наружу открыты только порт 25 (для диапазонов EOP) и 443 (панель). Порты 993 и 587 нужны одной панели на той же машине. Если понадобятся почтовые приложения на телефонах, их придётся открыть.
4. Лимиты памяти контейнеров MailExpert, `--max-old-space-size` для Node, параметры PostgreSQL по таблице.
5. Сеть Docker панели — в белый список блокировок mailcow.
6. Общий риск: у mailcow есть служебный контейнер с доступом к Docker socket, так что взлом админки mailcow теоретически даёт доступ ко всей машине, включая базу панели. Поэтому админку закрыть обязательно.
7. Одна точка отказа: бэкапы обеих частей держать у другого провайдера.

**Два отдельных сервера надёжнее:**
- отказ одного не роняет второй;
- взлом mailcow не даёт доступа к панели;
- узел можно переносить и менять ему IP, не трогая панель.

Стоит такая пара ненамного дороже одного сервера на 16 ГБ.

### 4.4 Один сервер на 250 ящиков: 4 vCPU / 8 ГБ

На 250 ящиков одного сервера на 4 ядра и 8 ГБ хватает на всё сразу, запас небольшой, но рабочий.

| Компонент | ГБ | Откуда цифра |
|---|---|---|
| Dovecot, 250 ящиков, с настройками | 0.3-1.1 | половина замера на 500 |
| Остальной mailcow (MariaDB, Rspamd, Postfix, SOGo, служебные) | 1-1.2 | замер, от числа ящиков почти не зависит |
| Node панели | 0.1-0.2 | замер на 500: до 0.35 |
| PostgreSQL | 0.2-1 | замер на 500 ящиках до 100 тысяч писем |
| Redis, Caddy, фронтенд | 0.1 | |
| ОС и Docker | 0.6 | |
| **Занято** | **2.3-4.2** | |
| **Под файловый кэш** | **3.8-5.7** | |

Без настроек Dovecot на 250 ящиках занимает около 2 ГБ (половина замера на 500), и занято выходит 4.0-5.1 ГБ. Замер на стенде 4 vCPU / 8 ГБ с 500 ящиками узла, 125 Gmail и 125 тысячами писем — в mail-node.md, раздел 6а.

Условия:
- в mailcow `SKIP_CLAMD=y`, `SKIP_OLEFY=y`, `SKIP_FTS=y` и настройки Dovecot из mail-node.md;
- PostgreSQL настроен: `shared_buffers` около 1 ГБ, `effective_cache_size` около 3 ГБ;
- Node запущен с `--max-old-space-size=1024`, у контейнеров панели заданы лимиты памяти;
- swap 2-4 ГБ как страховка от пиков, например после перезапуска, когда синхронизируются все ящики;
- диск NVMe;
- выполнены пункты совмещения из раздела 4.3: mailcow на localhost за Caddy, сертификат через Caddy, белый список, закрытая админка.

Память mailcow измерена в тесте с одним письмом на ящик; с настоящей почтой индексы Dovecot больше. После установки проверить `docker stats`.

Диск (почта по реальному заполнению, база панели и запас 20%):

| Среднее заполнение ящика | Почта 250 ящиков | Нужно NVMe |
|---|---|---|
| 200 МБ | 50 ГБ | ~100 ГБ |
| 500 МБ | 125 ГБ | ~200 ГБ |
| 1 ГБ | 250 ГБ | ~350 ГБ |

Когда переходить на 16 ГБ:
- ящиков больше 500;
- поиск по почте заметно тормозит;
- в `docker stats` под файловый кэш остаётся меньше 1 ГБ.

У большинства VPS-провайдеров тариф повышается без смены IP (например, в Hetzner Cloud). Поэтому стартовать с 8 ГБ безопасно.

Если серверов два, на 250 ящиков панели хватает 2 vCPU / 4 ГБ, а почтовый узел на 4 vCPU / 8 ГБ работает с большим запасом.

## 5. Экономия ресурсов на постоянных соединениях

**Что EOP даёт и чего не даёт.** EOP уже экономит ресурсы: антивирус и основной антиспам на его стороне. Сигнала о новом письме EOP не даёт: он доставляет письмо на узел по SMTP, а push-уведомления Microsoft Graph есть только у облачных ящиков Exchange Online. О доставке знает сам узел, поэтому «мост» строится от Dovecot к MailExpert.

**Сколько вообще можно выиграть.** Потолок — стоимость постоянных соединений. На стенде это около 1 ГБ на 500 ящиков; в mailcow под панелью — 3,9 ГБ, потому что сессий вдвое больше и каждая дороже (раздел 3).

| | Гибернация IDLE в Dovecot | Мост по событиям |
|---|---|---|
| Как работает | простаивающие соединения переезжают в общий процесс `imap-hibernate` (`imap_hibernate_timeout`). TLS-посредник убирается отдельно: режим login-процессов «много соединений на процесс» или, на одном сервере, IMAP без TLS по внутренней сети Docker | плагин push-уведомлений Dovecot с драйвером Lua (в образе mailcow есть `dovecot-lua`, Dovecot 2.3.21) шлёт в MailExpert HTTP-запрос «в ящик X пришло письмо». MailExpert забирает письмо коротким соединением. Постоянные соединения — только у ящиков, открытых в панели. Раз в 10-15 минут контрольная сверка |
| Экономия | заметная часть ~1 ГБ; вместе с уборкой TLS-посредника — почти весь | почти весь ~1 ГБ и во много раз меньше соединений |
| Задержка новых писем | мгновенно | 1-2 секунды |
| Изменения в MailExpert | нет | новый режим работы, вебхук, сверка по таймеру |
| Риски | в mailcow по умолчанию выключено, включается своим конфигом; процесс гибернации имеет доступ к почте всех ящиков | свой Lua-скрипт в mailcow, потерянные события закрывает сверка, больше движущихся частей |

«Активировать ящик перед отправкой» не нужно: отправка идёт по SMTP без IMAP-соединения, а копия в «Отправленные» кладётся коротким соединением.

**Gmail-ящики** через EOP и узел не идут. Их серверную сторону держит Google, нам каждый стоит около 100 КБ в панели. Свой push у Gmail (Gmail API + Pub/Sub) при нескольких проектах Google Cloud требует тему на каждый проект и публичный вебхук, а экономит около 50 МБ на 500 ящиков. Для Gmail оставляем постоянные соединения.

**Рекомендация и замер.** Гибернация вместе с общими процессами входа сделана: файл настроек Dovecot, [mail-node.md](../../operations/mail-node.md), раздел 3, шаг 4. На 500 ящиках Dovecot занимает около 0,5 ГБ в обычной работе и 2,2 ГБ в пике вместо 3,9 ГБ. Гибернация не работает, если клиент включил сжатие COMPRESS, поэтому MailExpert к ящикам узла его не включает; заодно память бэкенда в том же тесте упала с 740 до 337 МБ.
- **Мост по событиям** — если ящиков станет заметно больше 500.

## 6. Адаптивные квоты

- **Квота только ограничивает.** Ящик с квотой 1 ГБ и 50 МБ писем занимает на диске 50 МБ. Размер диска поэтому определяется реальным объёмом почты, а не суммой квот.
- **Зачем тогда адаптивность.** В mailcow сумма квот ящиков домена не может превышать квоту домена (feature request mailcow #6052 просит это ослабить). Фиксированные большие квоты исчерпали бы бюджет домена на бумаге при почти пустом диске. Адаптивные держат сумму квот рядом с реальным использованием. Тогда квота домена работает как честный бюджет диска, и один ящик не может занять всё место.

**Схема** (войдёт в PR 9 вместе с созданием ящиков):
- Настройки администратора:
  - начальная квота (300 или 500 МБ);
  - порог (осталось меньше 100 МБ);
  - шаг (например, +250 МБ);
  - потолок на ящик (например, 5 ГБ);
  - общий бюджет диска.
- Фоновая задача раз в 5 минут:
  1. Читает у mailcow заполнение всех ящиков одним запросом `GET /api/v1/get/mailbox/all`.
  2. Ящикам ниже порога поднимает квоту через `POST /api/v1/edit/mailbox`.
  3. При необходимости поднимает квоту домена, но только в пределах бюджета.
- Когда бюджет исчерпан, квота не растёт, а администратор получает уведомление и запись в журнале.
- В панели видно заполнение каждого ящика.
- **Риск.** Если за 5 минут придёт больше свободного места, письмо отклонят как «ящик переполнен», и EOP вернёт отправителю отказ. Защита — максимальный размер письма держать заметно меньше порога, например 25-35 МБ. Если этого окажется мало, увеличить порог или частоту проверки.

## 7. База данных панели

**Вывод: PostgreSQL оставляем.** Панель опирается на то, что он даёт в одной программе:
- транзакции и advisory-блокировки (в 9 файлах);
- полнотекстовый поиск и триграммы;
- JSONB (в 23 файлах) и `ON CONFLICT` (в 31);
- SQL есть в 61 файле, миграций 66.

Альтернативы и почему они не подходят:
- **SQLite** — пишет только один процесс за раз, а у нас одновременно синхронизируются 500 ящиков и работают сотрудники. Нет межпроцессных блокировок и триграмм.
- **MySQL и MariaDB** — полнотекстовый поиск слабее, триграмм нет, выигрыша по ресурсам нет.
- **ClickHouse и DuckDB** — аналитические, не для постоянных мелких записей.
- **CockroachDB и YugabyteDB** — тяжелее PostgreSQL.
- **MongoDB** — ни в чём не выигрывает.

Переезд на любую из них — это переписать весь слой данных ради сотен мегабайт.

**Где реальный выигрыш:**
1. **Настроить PostgreSQL.** В `docker-compose.yml` параметров нет, работают заводские: `shared_buffers` 128 МБ. Под 8 ГБ: `shared_buffers` около 2 ГБ, `effective_cache_size` около 5 ГБ, `random_page_cost` 1.1 под NVMe, разумный `work_mem`. Сделать до запуска.
2. **Пересмотреть индексы поиска.** Три триграммных индекса (тема, адрес и имя отправителя) частично дублируют поисковый вектор. Возможное сокращение индексов на 20-40% — оценка, проверить на реальных запросах.
3. **Ограничить срок хранения тел писем,** например 90 днями, а старые подгружать с почтового сервера при открытии. Такой путь в MailExpert уже есть. База сократится в 2-3 раза, но поиск по тексту старых писем уйдёт на почтовый сервер или пропадёт. Это продуктовое решение.
4. **Сжатие lz4 для колонок с телами** (PostgreSQL 14+): размер примерно тот же, процессор тратится меньше.
5. **PostgreSQL 18:** асинхронный ввод-вывод. Миграция через дамп и восстановление, проверять на копии.
6. **Внешний поисковый движок** (например, Meilisearch) — только если поиск станет узким местом.

## Открытые решения

1. Квоты: начальная (300 или 500 МБ), шаг, потолок на ящик, общий бюджет.
2. Сколько писем на ящик хранит панель и как долго хранятся тела — от этого зависят размер базы и поиск по старым письмам.
3. Будет ли массовая исходящая отправка — от этого зависит, хватит ли лимита EOP на тенант.
4. EOP остаётся при цене лицензий $1-2 за ящик в месяц? Без него понадобятся свой антивирус (+2-3 ГБ памяти) и своя репутация IP.
5. Раскладка по серверам: два сервера (рекомендуется) или один на 8-16 ГБ.
6. Три решения из ревизии EOP + mailcow ([eop-review.md](eop-review.md), «Решения владельца»): кто
   подписывает DKIM (EOP, mailcow или оба); явный фишинг — карантин администратору или «Спам»
   сотрудникам; DBEB — сразу при первом узле или после того, как он отработает на Internal Relay.
