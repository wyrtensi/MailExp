# Система раскатки MailExpert

Из каких модулей состоит развёрнутый MailExpert, что из них можно разносить по серверам, как
обновляется каждый модуль, в каком порядке и как откатывается, какие версии должны совпадать. Здесь
же — обновление из панели (раздел 9, с моделью угроз) и правила раскатки агентом.

Пошаговые инструкции не здесь: единая точка входа для оператора — [operations/README.md](../operations/README.md),
команды — в [deployment.md](../operations/deployment.md) и [mail-node.md](../operations/mail-node.md).
Исходный дизайн развёртывания —
[2026-09-21-deployment-design.md](../superpowers/specs/2026-09-21-deployment-design.md); ниже
отмечено, где реализация от него отошла.

Плейсхолдеры: `<PANEL_HOST>` — сервер панели (его адрес для SSH), `<APP_HOST>` — публичный адрес
панели (`<CF_HOST>` и/или `<DIRECT_HOST>`), `<MAIL_HOST>` — почтовый узел, `<PANEL_IP>` — публичный
IPv4 панели, `<PREFIX>` — каталог установки (по умолчанию `/opt/mailexpert`).

## 1. Модули

| Модуль | Что это | Образ / где живёт | Состояние |
|---|---|---|---|
| frontend | nginx: SPA и прокси `/api` на backend | `ghcr.io/wyrtensi/mailexpert-frontend:sha-<12>` | нет |
| backend | API, WebSocket, синхронизация IMAP/Gmail, очередь заданий, опросы узла и тенанта, миграции при старте; **один процесс** | `ghcr.io/wyrtensi/mailexpert-backend:sha-<12>` | в PostgreSQL и Redis |
| postgres | PostgreSQL 16, единственная база панели | `postgres:16-alpine`, том `<project>_postgres_data` | всё: пользователи, ящики, письма, журнал, зашифрованные пароли |
| redis | Redis 7: сессии, кэш | `redis:7-alpine`, том `<project>_redis_data` | сессии (`noeviction`) |
| tenant-worker | необязательный: EXO PowerShell за белым списком операций, подписывает ассерции Graph сертификатом приложения | `ghcr.io/wyrtensi/mailexpert-tenant-worker:sha-<12>`, профиль compose `tenant` | PFX и пароль — файлы на хосте, только чтение |
| edge: caddy | TLS для `<DIRECT_HOST>` (DNS-01 через Cloudflare) | `ghcr.io/wyrtensi/mailexpert-edge:sha-<12>`, **закреплён по digest** в `<PREFIX>/edge/.env` (`EDGE_IMAGE`) | сертификаты в томе `caddy_data` |
| edge: cloudflared | исходящий туннель к `<CF_HOST>` | `cloudflare/cloudflared:<версия>` из `deploy/edge/compose.yml` | нет (токен в `edge/.env`) |
| таймеры панели | `mailexpert-backup.timer` (restic в S3), `mailexpert-health.timer` (Healthchecks) | systemd на хосте панели, скрипты из `<PREFIX>/app/scripts/deploy` | `<PREFIX>/state/` |
| почтовый узел | mailcow и его скрипты хоста: `setup.sh`, таймер диапазонов EOP и файрвола, ночной бэкап узла | отдельный сервер; mailcow в `/opt/mailcow-dockerized`, копия репозитория MailExpert, копии скриптов в `/opt/mailexpert-node` | почта (vmail), mysql mailcow, `/etc/mailexpert-node/node.env` |

Внешние зависимости: Cloudflare (DNS, туннель, Access), Google (вход и OAuth-приложения для Gmail),
тенант Microsoft (EOP, Graph, EXO), S3-совместимое хранилище у другого провайдера (restic),
Healthchecks.io или совместимый сервис (пинги, оповещения в Telegram).

Модули панели (frontend, backend, postgres, redis, tenant-worker) — один compose-проект
(`docker-compose.yml` + `deploy/compose.prod.yml`); край — отдельный compose-проект `edge`, он
переживает обновления панели.

## 2. Связи и порты

```text
браузер ──443──> caddy (host network) ─┐
браузер ──> Cloudflare ──туннель──> cloudflared (host network) ─┤
                                                               v
                                               127.0.0.1:8080 frontend ──> backend:3000
                                                                              │  сеть compose
                                     postgres:5432 <──┬───────────────────────┤
                                     redis:6379    <──┘                       ├──> tenant-worker:8080 ──> Graph, EXO (HTTPS)
                                                                              │
                                  <MAIL_HOST>: 443 (API mailcow), 993, 587 <──┤  с <PANEL_IP>
                                  Gmail, Google OAuth, IMAP/SMTP провайдеров <┘
EOP ──25──> узел (mailcow) ──25──> EOP (smart host)
```

| Откуда → куда | Порт | Доступ |
|---|---|---|
| интернет → caddy | 80, 443 | режимы `direct`/`both`; иначе закрыт `ufw` |
| caddy, cloudflared → frontend | `127.0.0.1:8080` | только loopback |
| frontend → backend; backend → postgres, redis, tenant-worker | сеть compose | наружу не публикуются; к исполнителю — общий токен `TENANT_WORKER_TOKEN` |
| backend → `<MAIL_HOST>` | 443 (API), 993 (IMAP), 587 (SMTP) | ключ API mailcow с «Allow API access from» = `<PANEL_IP>`; 993/587 файрвол узла открывает только `<PANEL_IP>` |
| EOP → узел | 25 | только диапазоны EOP (ipset, таймер узла) |
| узел → EOP | 25 | smart host `<EOP_HOST>` |
| таймеры панели и узла → S3, Healthchecks | 443 | исходящие |

Из этого следует: панель не хранит IP узла (только `<MAIL_HOST>`), узел знает `<PANEL_IP>` (файрвол,
fail2ban, API). Смена IP панели — правка `--panel-ip` на узле и списка адресов в настройках узла;
смена IP узла — только DNS.

## 3. Что можно разносить по серверам

| Модуль | Где может жить | Почему так |
|---|---|---|
| frontend, backend, postgres, redis | **только вместе**, один хост, один compose-проект | `backup.sh`, `restore.sh`, `update.sh` и `status.sh` выполняют `pg_dump`/`psql` внутри контейнера `postgres`; готовность проверяется на loopback; backend — один процесс (ниже) |
| tenant-worker | **на хосте панели**, в её compose-проекте (другой хост не поддерживается) | backend ходит к нему по `TENANT_WORKER_URL` (`http://tenant-worker:8080` внутри сети compose): без TLS, с общим токеном. Адрес другого хоста технически указать можно, но токен и операции шли бы открытым HTTP, а скрипты такой раскладки не ставят и не проверяют |
| edge (caddy, cloudflared) | на хосте панели | проксирует на `127.0.0.1:<APP_HTTP_PORT>` |
| почтовый узел | **всегда отдельный сервер**, ровно один на панель | mailcow сам занимает 80/443 (ACME для `<MAIL_HOST>`), на хосте панели 443 у Caddy; настройки узла в панели — одна запись (одно имя узла, один ключ API) |
| таймеры бэкапа и проверки | на том сервере, который бэкапят и проверяют | панель и узел — каждый свой |

**Не поддерживается** (и почему):

- **Узел на одном сервере с панелью.** В дизайне 2026-09-21 это раскладка «Один сервер» (Caddy
  проксирует ACME и админку mailcow), но эта часть (PR 9) не сделана: скрипты не умеют проксировать
  на mailcow, порт 443 занят краем панели. Актуально — [mail-node.md, раздел 2](../operations/mail-node.md).
- **Внешняя или управляемая PostgreSQL.** `DB_HOST` backend принимает, но compose всё равно
  запускает свой `postgres`, а бэкап, восстановление, обновление (дамп перед обновлением, проверка
  места) и `status.sh` работают внутри этого контейнера. Чтобы поддержать, нужны: дамп и
  восстановление через сеть с клиентом нужной версии, отключение сервиса `postgres` оверлеем,
  другая оценка места. Отдельная задача, если понадобится.
- **Несколько реплик backend.** Восстановление пароля ящика узла, охрана очереди перемещений,
  соединения IMAP и WebSocket держат состояние в памяти процесса
  ([mail-node.md, раздел 1](../operations/mail-node.md)).
- **Несколько почтовых узлов на одну панель и один узел на несколько панелей.** Настройки узла —
  одна запись; узел знает адреса одной панели.
- **tenant-worker на отдельном хосте** — не поддерживается (не «невозможно»): `TENANT_WORKER_URL`
  может указывать на другой хост, но связь — открытый HTTP с общим токеном, а установка, обновление и
  проверка исполнителя рассчитаны на compose-проект панели. Чтобы поддержать (например, Windows-хост),
  нужны TLS между backend и исполнителем, привязка токена к адресу и своя установка исполнителя.
- **Высокая доступность.** Один сервер панели; переезд — плановый, с простоем
  ([deployment.md, раздел 6](../operations/deployment.md)).

## 5. Версии и совместимость

**Версия** — тег образов `sha-<первые 12 символов коммита>` на `main`. Его публикует джоба `images`
CI после зелёной сборки (backend, frontend, edge, tenant-worker — все четыре с одним тегом).
Выпусков (GitHub releases, semver) в этом репозитории нет; версия — коммит. Боевой канал —
`latest`: сборка, которую владелец продвинул как готовую к проду (workflow `promote.yml`, раздел 9);
сервер и тогда запускает её `sha-<12>`, а не изменяемый тег.

| Пара | Правило |
|---|---|
| frontend ↔ backend | всегда один тег (`MAILEXPERT_VERSION`); `install.sh` проверяет, что `/api/version` отдаёт ожидаемый коммит |
| backend ↔ tenant-worker | один тег: оверлей берёт тот же `MAILEXPERT_VERSION`, `update.sh` тянет образ исполнителя до бэкапа. Исполнитель старее панели (образ собран руками) — панель показывает предупреждение по ответу `unknown_op`, операции нового выпуска не выполняются |
| backend ↔ база | миграции только вперёд, применяются backend при старте под advisory lock; версия миграции — имя файла (`NNNN_name.sql`), поэтому влитую в `main` миграцию **никогда не переименовывают** и не меняют (иначе база и код разойдутся в списке версий). Код старее схемы не поддерживается: `status.sh --target` называет это проблемой («older than the database schema»), путь назад — дамп перед обновлением. Если схему прочитать не удалось, ожидающие миграции неизвестны (`null` в JSON, `unknown` в тексте) и считаются присутствующими |
| панель ↔ скрипты узла | общего протокола нет: панель работает только через API mailcow. Скрипты хоста узла — это коммит копии репозитория на узле. Правило: когда обновление панели меняет `scripts/deploy/mail-node/` (`update.sh` и `status.sh` пишут об этом), на узле — тот же коммит и `setup.sh` |
| панель ↔ правило раскладки спама на узле | узел держит записанную версию правила, пока администратор не применит новую (перезапуск Dovecot). Панель сама читает состояние (`ok`/`outdated`/`missing`) и показывает предупреждение; `status.sh` выводит последнее известное |
| панель ↔ mailcow | проверки версии mailcow в коде нет; панель проверена на mailcow `2026-09` (стенд). Обновление mailcow — отдельно от панели, после — `setup.sh` |
| edge ↔ панель | не связаны по протоколу; Caddy закреплён по digest, `update.sh` меняет его, только когда между версиями изменился `deploy/edge/Dockerfile` (раздел 6) |

## 6. Обновление по модулям

| Модуль | Как обновляется | Кто запускает | Откат |
|---|---|---|---|
| панель (frontend, backend, миграции) | `update.sh sha-<12>`: проверки, `pg_dump` в `backups/pre-update-<старый>.dump` и снимок restic `pre-update`, `install.sh --version` (checkout, `.env`, `up`, ожидание готовности до 10 минут) | оператор или агент по SSH | без новых миграций — `install.sh --version <старый>`; с миграциями — восстановление дампа ([deployment.md, «Откат обновления»](../operations/deployment.md)) |
| tenant-worker | вместе с панелью тем же `up` (профиль `tenant`) | — | вместе с панелью |
| cloudflared | версия в `deploy/edge/compose.yml`; `install.sh` копирует файл и делает `up` края при каждом обновлении | — | вместе с панелью |
| Caddy (образ edge) | `EDGE_IMAGE` закреплён по digest. Когда между версиями меняется `deploy/edge/Dockerfile`, `update.sh` скачивает `mailexpert-edge:<новая версия>` до бэкапа, сохраняет прежний `EDGE_IMAGE` в `state/edge-image.previous` и очищает его, `install.sh` закрепляет новый | `update.sh` (и кнопка в панели) | `rollback.sh` и автооткат возвращают прежний; вручную — digest из `state/edge-image.previous` в `EDGE_IMAGE` и `install.sh` |
| Caddyfile, compose края, юниты systemd | `install.sh` (его вызывает `update.sh`) пишет их из нового коммита; Caddy перезапускается, если Caddyfile изменился | — | вместе с панелью |
| postgres, redis | тег мажорной версии в `docker-compose.yml`; хост тянет образ только если его нет, поэтому фактически версия заморожена с установки. Смена мажорной версии PostgreSQL скриптами не поддерживается (нужен дамп и восстановление в новый том): `status.sh --target` называет её проблемой, `update.sh` отказывает с кодом 2 до бэкапа; другие смены образов — строка `info:` | — | — |
| скрипты узла | на узле: `git -C /opt/mailexpert-node-src fetch` и checkout коммита панели, `setup.sh --dry-run`, затем `setup.sh` | оператор или агент по SSH на узел | checkout прежнего коммита и `setup.sh` |
| mailcow | его `./update.sh` в `/opt/mailcow-dockerized`, затем `setup.sh` без параметров и, если он изменил `mailcow.conf`, `docker compose down && up -d` ([mail-node.md, раздел 3](../operations/mail-node.md)) | оператор | средствами mailcow; данные — бэкап узла |
| ОС | `unattended-upgrades` (ставит `install.sh`) | — | — |

### Порядок, когда меняется несколько модулей

1. **Предпроверка** без изменений: `status.sh --target sha-<12>` на панели (`update.sh --check` —
   то же). Проблемы (`problem:`) устраняются до обновления; `next:` — шаги вне `update.sh`,
   `info:` — справка.
2. **Обновление mailcow** — не в одном окне с панелью: по отдельности легче понять, что сломалось.
3. **Панель**: `update.sh sha-<12>`, отдельно от SSH-сессии (`systemd-run`,
   [README.md, раздел 9](../operations/README.md)); tenant-worker обновляется вместе с ней, одним `up` и с тем же
   тегом. Порядок «сначала исполнитель, потом панель» из mail-node.md («Обновление до версии с
   решениями после этапа 7») относился к исполнителю, собранному на хосте; с образом из GHCR оба
   переходят на новую версию одновременно, а образ исполнителя `update.sh` скачивает до бэкапа.
4. **Узел**, если изменились его скрипты: тот же коммит на узле, `setup.sh --dry-run`, `setup.sh`.
5. **Действия в панели**, о которых она предупреждает: применить правило раскладки спама, «Применить
   настройки» узла, «Проверить и исправить» антиспам-политику тенанта.
6. **Caddy** отдельно не обновляется: если изменился его образ, это сделал `update.sh` (шаг 3).
7. **Проверка после**: `status.sh` без проблем, `healthcheck.sh` (код 0), вход через `<APP_HOST>`,
   статус ящиков в админке.

## 7. Откат

Сначала — состояние сервера сейчас (`status.sh`: `version`, `checkout`, `running`). Коды
`update.sh`: `0` — обновлено; `1` — переключение началось, новая версия не поднялась; `2` — неверный
ввод или запрещающее состояние, ничего не изменено; `3` — сбой до переключения (образ, бэкап, любая
другая команда), ничего не изменено. После `2` и `3` откатывать нечего.

- **Панель без новых миграций** (`status.sh --target` показал `pending_migrations none` — не
  `unknown` — и `update.sh` написал «no migration was recorded as applied»):
  `install.sh --prefix <PREFIX> --version <старая версия>` — данные не теряются.
- **Панель с новыми миграциями или когда это неизвестно**: только через дамп `backups/pre-update-<старая>.dump`, по шагам
  [deployment.md, «Откат обновления»](../operations/deployment.md). Теряется всё, записанное после
  обновления; почта догружается синхронизацией. Одной командой — `rollback.sh --to <старая>` (с
  подтверждением; раздел 9). Когда откатываться — решает человек; сам `update.sh` не откатывает,
  а обновление из панели откатывается само только без миграций (раздел 9).
- **Узел**: скрипты — прежний коммит и `setup.sh`; данные — `node-restore.sh` только на чистый сервер
  ([mail-node.md, раздел 8](../operations/mail-node.md)).
- **Признаки, что откат нужен**: `update.sh` вышел с кодом 1 (не поднялось за 10 минут), backend в
  цикле перезапуска, `running` в `status.sh` не тот коммит, массовые ошибки входа в ящики после
  обновления.

## 8. Инструменты раскатки

| Скрипт | Где | Что |
|---|---|---|
| `install.sh` | панель | установка и повторное применение конфигурации; идемпотентен |
| `configure.sh` | панель | секреты владельца из stdin |
| `status.sh` | панель | **только чтение**: версии (install.conf, checkout, запущенная сборка, теги образов), готовность, контейнеры, исполнитель, образ края, место, бэкапы, миграции, состояние правила спама; с `--target` — коммит, образы в реестре (`ok`/`missing`/`unknown`, если реестр не ответил), ожидающие и «лишние» миграции (`null`, если схема не прочитана), мажорная версия PostgreSQL, шаги вне `update.sh` (`next`) и справка (`info`); `--json` для агента, при сбое самого скрипта — `{"error": ...}` |
| `update.sh` | панель | обновление до `sha-<12>` или `latest`; `--check` — то же, что `status.sh --target`; коды 0/1/2/3 (раздел 7) |
| `updater.sh` | панель | исполнитель запросов из панели (юниты `mailexpert-updater.path`/`.service`, раздел 9) |
| `rollback.sh` | панель | откат к версии до обновления через её дамп, с подтверждением |
| `scripts/ci/promote-latest.sh` | GitHub Actions (`promote.yml`) | продвижение сборки в канал `latest` |
| `backup.sh`, `restore.sh` | панель | бэкап и восстановление |
| `healthcheck.sh` | панель | проверка по таймеру и вручную |
| `mailexpert-cli.sh` | панель | администрирование панели из командной строки |
| `mail-node/setup.sh` (`--dry-run`) | узел | настройки хоста узла, файрвол, таймеры |
| `mail-node/node-backup.sh`, `node-restore.sh` | узел | бэкап и восстановление узла |

Раскатка агентом — скилл [`.claude/skills/mailexpert-rollout/SKILL.md`](../../.claude/skills/mailexpert-rollout/SKILL.md)
и раздел в [AGENTS.md](../../AGENTS.md): та же последовательность, что у человека (предпроверка →
письменный план → подтверждение → скрипты → проверка), с явными точками подтверждения перед
необратимыми шагами.

## 9. Обновление из панели (PR B)

Администратор видит в панели, что владелец продвинул новую сборку, и обновляет кнопкой; хост делает
то же, что `update.sh`, с теми же гарантиями. Контейнер панели при этом **не получает сокет Docker**
и не выполняет команды хоста: он только кладёт файл-запрос в спул и читает файлы-результаты.

### Канал `latest`

Панель предлагает обновление только из канала **`latest`**: это сборка, которую владелец счёл
готовой к проду, а не просто последний зелёный `main`. Зелёный CI — условие, но не решение.

- **Продвижение** — шаг владельца: workflow `promote.yml` (`workflow_dispatch`, параметр `sha`:
  коммит или `sha-<12>`, пусто — голова `main`; `dry_run` — только проверка). Скрипт
  `scripts/ci/promote-latest.sh` проверяет, что коммит на `main` и что его образы (backend,
  frontend, edge, tenant-worker) с тегом `sha-<12>` есть в GHCR (джоба `images` публикует их только
  после зелёного CI), ставит каждому тег `latest` через `crane tag` (те же байты манифеста — тот же
  digest, проверяется после) и **последним** переносит лёгкий git-тег `latest` на коммит. Тег
  `sha-<12>` не меняется, ничего не пересобирается. `publish.yml` (semver-образы для тегов `v*`)
  тег `latest` больше не ставит — иначе он перебивал бы канал. Workflow запускается только с `main`
  (`if: github.ref == 'refs/heads/main'`). **Обязательная настройка репозитория**: ruleset на тег
  `latest`, разрешающий создавать, двигать и удалять его только GitHub Actions и владельцу, — иначе
  любой с правом push тегов направил бы панели на другой коммит (хосты и тогда не ставят `latest` вне
  `main` или старее текущей версии и сверяют digest образов).
- **Разрешение канала** (`lib/channel.sh`): `update.sh latest` (или `--version latest`),
  `update.sh --check latest` и `status.sh --target latest` делают `git fetch` тега `latest` с
  принудительным refspec (обычный fetch не двигает уже скачанный тег) и превращают его в
  `sha-<12>`. Затем сравнивают digest образов `latest` и `sha-<12>` (все четыре: backend, frontend,
  edge, tenant-worker; `docker manifest inspect -v`): разные — отказ (продвижение не доделано или тег сдвинут руками), реестр не
  ответил — предупреждение (образы всё равно тянутся по `sha-<12>`). Сервер всегда запускает
  `sha-<12>`, никогда изменяемый тег: откат, дамп `pre-update-<sha>` и проверка `/api/version`
  остаются однозначными.
- **Откуда панель узнаёт о новой версии**: backend (`services/panelUpdate/latest.js`) читает git-тег
  через GitHub API (`/git/ref/tags/latest`, публичный репозиторий, без токена, через `safeFetch`) и
  сравнение с текущим `BUILD_SHA` (`/compare/<текущий>...<latest>`: `ahead_by`, статус). Кэш 6 часов,
  после ошибки — повтор не раньше чем через 15 минут, при исчерпанном лимите GitHub (403/429 с
  `x-ratelimit-remaining: 0`) — не раньше сброса; последний удачный ответ сохраняется;
  карточка «Обновление панели» при открытии просит свежую проверку (`GET /api/admin/update?refresh=1`,
  backend выполняет её не чаще раза в минуту), так что продвинутая сборка видна сразу, а не через
  6 часов; опрос во время обновления идёт по кэшу. `UPDATE_CHECK_DISABLED` выключает проверку. Старый `/api/update` (баннер по semver) не тронут.

### Как это устроено

```text
админ: «Обновить до sha-X» (подтверждение)
  → POST /api/admin/update {target, confirm}   только администратор; запись panel.update_requested
      → request/<uuid>.tmp (O_EXCL, 0600, fsync) → rename → request/<uuid>.json
  → хост: mailexpert-updater.path (PathExistsGlob=request/*.json)
      → mailexpert-updater.service (oneshot, root, TimeoutStartSec=4h) → updater.sh:
          не больше 10 запросов — переименованием в state/updater/incoming (только root),
          остальное удаляется; проверка каждого (ниже); не больше одной проверки и одного
          обновления за запуск; запрос с id, для которого уже есть результат, — отбрасывается,
          цель: ровно продвинутый latest, на main, потомок HEAD, не откаченная версия,
          status.sh --target <sha> --json → problems: blocked; сбой скрипта: error,
          update.sh <sha> → лог state/updater/<uuid>.log, хвост лога в результат каждые 5 с,
          result/<uuid>.json (temp + rename): checking → updating → succeeded | failed |
              rolling_back → rolled_back | rollback_failed
  → панель: GET /api/admin/update каждые 3 с, пока идёт обновление; переживает перезапуск backend
```

- **Спул**: `<PREFIX>/state/update-spool/request/` — владелец uid backend, `0700`, смонтирован в
  backend на запись. Uid `install.sh` спрашивает у самого образа (`docker run --rm --network none
  --entrypoint id <образ backend> -u`) и пишет в `state/spool-uid`; не ответил — прежняя запись или
  1000 (`USER node`). На облачных образах Ubuntu uid 1000 — это часто первый пользователь (`ubuntu`):
  он тоже может класть запросы. Это не расширяет его права (у него обычно есть sudo, а запрос проходит
  те же проверки), но на хосте, где uid 1000 — чужой непривилегированный пользователь, это стоит
  учитывать. `result/` — root, `0755`, смонтирован только на чтение
  (`deploy/compose.prod.yml`, путь хоста — `UPDATE_SPOOL_HOST_DIR` в `.env`, его пишет
  `install.sh`). `install.sh` создаёт каталоги при каждом запуске, с systemd и без (иначе dockerd
  создал бы точки монтирования от root). Рабочий каталог исполнителя `state/updater/` (лок, логи,
  `incoming/`) — только root, вне спула.
- **Запрос** — ровно `{id, action: "check"|"update", target, requestedAt, requestedBy}` до 4096 байт;
  исполнитель использует только `action` и `target`, `requestedBy` пишет в журнал после очистки.
- **Результат** — `{id, action, target, state, terminal, message, from, receivedAt, updatedAt,
  startedAt, finishedAt, exitCode, preflight{ok, problems, warnings, next, info, pendingMigrations,
  migrationsApplied}, autoRollback, next, log, logFile, journal}`; хранятся 20 последних. Результат
  пишется только для запроса, взятого в этом запуске, целиком и заново (в памяти, temp + rename),
  никогда не читается обратно и не дописывается: запрос с id уже готового результата отбрасывается
  без записи (строка в журнале хоста), иначе он перекрасил бы `succeeded` в `refused`.
  `result/updater.json` (`{installed, version, updatedAt, rolledBack}`) пишут `install.sh` при установке юнитов
  и исполнитель при каждом запуске: без него карточка пишет «механизм обновления не установлен»,
  а API отвечает 503. `rolledBack` — версия, с которой откатились (`rollback.sh` или автооткат,
  `state/rolled-back-version`): хост и панель не предлагают её снова, пока не продвинута более новая
  сборка; удачное обновление запись снимает, как и `install.sh`, когда эта версия снова запущена и
  готова (её вернули по SSH через `update.sh` или `install.sh --version`). Если backend не может писать в `request/` (другой uid),
  API отвечает 503 `spool_not_writable` с подсказкой перезапустить `install.sh`.
- **Занятость**: backend не принимает новый запрос, пока в `request/` есть `*.json` (или свежий
  `*.tmp`) или последнее обновление не в конечном состоянии (если результат не обновлялся 30 минут —
  считается зависшим). Запросы пишутся по одному под внутренним локом. На хосте отдельно —
  `update.lock` (отказ «an update, rollback or restore is running now») и лок исполнителя.
- **Юниты** ставит и обновляет `install.sh` (с systemd, когда в коммите есть `updater.sh`), на
  новых и существующих установках; `update.sh` вызывает `install.sh` новой версии, так что юниты
  всегда текущие. **Исполнитель не перезапускает сам себя**: `install.sh` переписывает файлы юнитов,
  делает `daemon-reload` и перезапускает только `.path` (остановка path-юнита не останавливает
  запущенный им сервис); `.service` не перезапускается и не останавливается — иначе systemd убил
  бы обновление на полпути. Новая версия юнита действует со следующего запуска. `updater.sh` сам
  переписывается checkout'ом во время работы, поэтому всё определено до `main`, а `main` вызывается
  одной строкой (как в `update.sh`).
- **Журнал**: `panel.update_requested` (кто нажал), `panel.update_started`, `panel.update_finished`,
  `panel.update_failed` (`failed`, `rolled_back`, `rollback_failed`, `refused`, `blocked`, `error`).
  Backend перезапускается посреди обновления, поэтому последние три пишет сверка
  (`services/panelUpdate/reconcile.js`: при каждом GET и раз в 30 с), без повторов по
  `details.requestId` и от имени того, кто запросил.

### Безопасность: модель угроз

Граница — каталог `request/`: по одну сторону контейнер backend, который может быть скомпрометирован
(уязвимость в зависимостях, украденная сессия администратора), по другую — root на хосте.

| Угроза | Защита |
|---|---|
| Выполнение команд хоста через запрос | Запрос не попадает ни в оболочку, ни в аргументы, ни в пути: из него берутся только `action` (`check`/`update`) и `target`, прошедший `^sha-[0-9a-f]{12}$`; имя файла — `<uuid>.json`. Строгая схема в `jq`: ровно пять ключей, типы и длины, `id` = имени файла |
| Символьная ссылка, жёсткая ссылка, FIFO, каталог вместо файла (чтение файлов root, зависание) | Каждая запись сначала переименовывается в `state/updater/incoming` (только root): переименование переносит ссылку как ссылку, после этого контейнер не может подменить запись. Затем `stat` без разыменования: обычный файл, владелец — uid backend (`state/spool-uid`), одна ссылка, 1..4096 байт; чтение один раз, `head -c 4096`. Иначе — отказ, запись удаляется (`rm` ссылок не разыменовывает). Жёсткую ссылку на файл хоста контейнер сделать не может (видит только спул), но число ссылок всё равно проверяется |
| Подмена файла между проверкой и чтением (TOCTOU) | Проверяется и читается уже перенесённая запись в каталоге root; удержанный контейнером дескриптор даёт менять содержимое, но читается оно один раз и проверяется после чтения |
| Обход решения владельца: установка непродвинутой версии, откат на старую, чужая ветка (скомпрометированный админ или backend) | Цель — ровно коммит, на который сейчас указывает тег `latest` (после `git fetch` с принудительным refspec), он на `origin/main`, строго потомок текущего `HEAD`, не версия, с которой откатились, и digest образов `latest` совпадает с `sha-<12>`. Любая другая версия — только `update.sh` по SSH; откат — только `rollback.sh` по SSH |
| Перезапись чужого результата (запрос с id готового обновления) | Результат пишется только для запроса этого запуска и заново; при существующем `result/<id>.json` запрос отбрасывается без записи, журнал панели не получает ложного `panel.update_failed` |
| Обновление на сломанную или небезопасную сборку | Те же проверки, что у человека: `status.sh --target` (образы в реестре, место, мажорная версия PostgreSQL, база новее цели, standby, занятый `update.lock`) — при любой проблеме обновление не начинается; затем `update.sh` со своими проверками, дампом и снимком restic |
| Отказ в обслуживании: поток запросов, мусор, огромные файлы | За запуск каталог разбирается целиком (иначе path-юнит перезапускался бы в цикле): берутся не больше 10 запросов, остальные удаляются без результатов (одна строка в журнале), так что поток не держит исполнитель часами и не забивает `result/` файлами; из взятых — не больше одной проверки и одного обновления, остальное — отказ. Мусорные имена удаляются; `*.tmp` старше 5 минут удаляются. Худшее — лишние запуски `status.sh`, не эскалация |
| Отказ в обслуживании через предел запусков systemd | Если запуски всё же пойдут подряд (сбой самого исполнителя до разбора каталога), `StartLimitBurst=30` за 10 минут останавливает сервис, а path-юнит перестаёт следить: кнопка молчит, пока администратор хоста не выполнит `systemctl reset-failed mailexpert-updater.service mailexpert-updater.path && systemctl start mailexpert-updater.path` (или `install.sh`). Разбор каталога идёт до всего, что может упасть, поэтому контейнер сам довести до этого не может; при этом обновления по SSH работают как обычно |
| Утечка секретов в контейнер через результат | В результат идут только строки скриптов с префиксом `[mailexpert] ` (не вывод команд), без строк вида `...PASSWORD=`/`SECRET=`/`TOKEN=`/`KEY=`; скрипты и так не печатают секреты вне терминала (ключ восстановления restic — только в терминал), а адрес репозитория в сообщениях печатается без учётных данных (`redact_url`). Полный лог — на хосте, `0600` |
| Подмена результатов | `result/` смонтирован только на чтение; результаты пишутся во временный файл и переименовываются. Backend всё равно разбирает их как данные (тип, размер, схема) |
| Подмена версии `latest` | Git-тег двигает только `promote.yml` с `main` (ruleset на тег `latest` — обязательная настройка); хост не ставит `latest` вне `main` и старее текущей версии, сверяет digest всех четырёх образов `latest` и `sha-<12>`; сервер запускает только `sha-<12>` |
| Действие от имени администратора без его ведома | Только администратор (`requireAdmin`), подтверждение в интерфейсе (`confirm` = `target`), запись в журнал с тем, кто нажал |

Тесты отказов — `scripts/deploy/test/updater.bats` (ссылки, FIFO, чужой владелец, размер, схема,
перевод строки в цели, не `latest`, `latest` вне `main`, даунгрейд, откаченная версия, повтор id,
занятый лок, поток запросов) и `backend/src/services/panelUpdate/*.test.js`.

### Откат

- **Автооткат только когда точно известно, что миграции не применялись**: предпроверка прочитала
  схему (`pendingMigrations` — пустой список, не `null`), `update.sh` вышел с кодом 1 и число
  записанных миграций не изменилось. Тогда исполнитель возвращает образ Caddy, если обновление его
  меняло, и запускает `install.sh --version <старая>` (итог `rolled_back` или `rollback_failed`).
  Иначе — `failed` и ссылка на runbook: откат через дамп теряет данные, решает человек. Автооткат —
  только после кода 1; код 2 и 3 — ничего не изменено, откатывать нечего; любой другой код (сигнал,
  убитый процесс) — `failed` без отката: что успело измениться, неизвестно.
- **`rollback.sh`** (решение владельца по вопросу 1): ручной, с подтверждением (ввод версии или
  `--confirm <версия>`). До остановки: проверки, образы старой версии и место — размер текущей базы
  плюс дамп на диске Docker (восстановленная копия лежит рядом с живой базой). Дальше: дамп
  `pre-update-<старая>.dump` в новую базу `<db>_rollback`; подмена переименованием — сначала живой
  базе запрещаются новые подключения (`ALLOW_CONNECTIONS false`, иначе проверка здоровья
  переподключалась бы между завершением сеансов и переименованием), затем до 5 попыток завершить
  сеансы и переименовать в одной транзакции; не вышло — база возвращается как была, панель
  запускается снова. Прежняя база остаётся `<db>_before_rollback_<время>` (имя базы обрезается до
  30 символов, чтобы уложиться в 63 байта). Затем возврат образа Caddy, `install.sh --version`,
  запись откаченной версии (`state/rolled-back-version`) и, если у старой версии нет `updater.sh`,
  отключение юнитов исполнителя. Прерванный после подмены запуск повторяется чисто
  (`state/rollback-in-progress`: повтор только переключает код); если `install.conf` уже говорит о
  целевой версии, скрипт велит закончить `install.sh --prefix <PREFIX>`. Панель на `rollback.sh`
  только ссылается и никогда его не запускает.
- Итог обновления — пинг `HEALTHCHECK_PING_URL` (его шлёт `update.sh`) и результат; строки `next:`
  (узел) показываются в карточке как «нужно сделать вручную». Узел кнопкой не обновляется.
  Автообновления по расписанию нет.

## 10. Открытые вопросы и решения

Решено:

- **Канал версий** (владелец): боевой канал — `latest`, только продвинутые владельцем сборки
  (раздел 9).
- **`git fetch` в `status.sh --target`** — допустим (как в `update.sh`); не выполняется, пока
  обновление держит `update.lock`.
- **Язык**: скилл и `AGENTS.md` — по-английски (инструкции агенту), документация по эксплуатации —
  по-русски.
- **Откат скриптом** (владелец, 2026-10): `rollback.sh` с подтверждением, без автозапуска; панель
  только ссылается на него (раздел 9).
- **Образ Caddy** (владелец, 2026-10): обновляется вместе с панелью, когда меняется
  `deploy/edge/Dockerfile` (образ собирается из него; Caddyfile и compose края `install.sh` пишет и
  так): `update.sh` скачивает его до бэкапа (сбой — код 3, ничего не изменено), сохраняет прежний
  `EDGE_IMAGE` в `state/edge-image.previous`, `install.sh` закрепляет новый по digest; откат его
  возвращает.
- **Правило цели кнопки** (уточнено при ревью PR B): только ровно продвинутый `latest`, на `main`,
  потомок текущей версии и не версия, с которой откатились. Любой другой коммит `main` — только
  `update.sh` по SSH; продвинутая сборка старее текущей кнопкой не ставится — это откат, он только по
  SSH.
