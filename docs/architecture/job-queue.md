# Очередь заданий

Общая долговечная очередь работы, которая выполняется позже и в фоне и переживает перезапуск backend.
Первый вид заданий — `send_message`: отмена отправки (5 секунд) и отложенная отправка. С этапа 7a EOP на
ней же идут задания тенанта Microsoft (раздел «Задания тенанта» ниже). Дальше предполагаются напоминания
follow-up, автоответы и отложенные действия с ящиками.

Код: `backend/src/services/jobQueue.js` (очередь), `backend/src/services/sendQueue.js` (вид `send_message`),
`backend/src/services/sendDelivery.js` (сама отправка), `backend/src/routes/scheduled.js` (управление
ожидающими письмами). Схема — миграция `0087_job_queue.sql`.

Очередь DB-first перемещений (`services/moveQueue.js`, таблица `message_moves`) остаётся отдельной: она
держит в памяти защиту uid от синхронизации и группирует MOVE по папкам, это не общая очередь.

## Таблица `jobs`

| Колонка | Смысл |
|---|---|
| `kind` | вид задания, по нему выбирается обработчик |
| `payload` | параметры: только идентификаторы и ссылки, никакого содержимого письма |
| `run_at` | когда задание созреет |
| `status` | `queued`, `running`, `done`, `failed`, `cancelled`, `needs_attention` |
| `attempts`, `max_attempts` | попытки; после последней неудачи — `failed` |
| `last_error`, `error_code` | текст без секретов и стабильный код для клиента |
| `claim_token`, `claimed_at`, `lease_until` | захват воркером и его аренда |
| `effect_started_at` | обработчик начал необратимый шаг (письмо ушло на сервер) |
| `dedupe_key` | повторный enqueue с тем же `(kind, dedupe_key)` возвращает уже созданное задание |
| `created_by`, `account_id` | кто поставил и о каком ящике речь; при удалении ящика `account_id` становится NULL |
| `finished_at` | когда стало `done` или `cancelled`; такие строки удаляются через 7 дней |

`failed` и `needs_attention` хранятся 30 дней после последнего изменения (`JOB_KEPT_FAILED_MS`), список
показывает, до какого числа, потом задание удаляется вместе с письмом.

Перед удалением ящика (оба пути: `DELETE /api/accounts/:id` и `services/mailNode/mailboxDeletion.js`)
`failJobsOfDeletedAccount` переводит его ожидающие и неотправленные задания в `failed` с кодом
`account_missing`: автор получает уведомление, журнал — `message.send_failed`, письмо остаётся в списке
(для правки). Задание, которое как раз выполнялось, находит ящик пропавшим и падает с тем же кодом.

Письмо задания `send_message` лежит отдельно, в `outgoing_messages` (`compose` — что писал автор,
`summary` — тема, адресаты и число вложений для списка, `mail` — собранное письмо), чтобы списки
заданий не читали ни текст, ни вложения. Оно удаляется, как только письмо ушло или
задание отменено; у `failed` и `needs_attention` остаётся, чтобы письмо можно было отправить снова.

## Как работает воркер

- Опрос раз в секунду (`JOB_POLL_MS`) и внутренний таймер на ближайший `run_at`, поэтому письмо с окном
  отмены уходит через 5 секунд, а не на секунду позже. LISTEN/NOTIFY не используется: backend — один
  процесс, а PGlite в тестах его не умеет. Если процессов станет несколько, их безопасность обеспечивает
  захват, а не уведомления.
- Захват: `UPDATE … WHERE id IN (SELECT … FOR UPDATE SKIP LOCKED)` — два процесса никогда не берут одно
  задание. Берутся только виды, зарегистрированные в этом процессе.
- Аренда 60 секунд продлевается каждые 20 секунд, пока обработчик работает. Любая запись о захвате
  проверяет `claim_token`, поэтому воркер, чей захват уже сняли, не может завершить задание второй раз.
- Выметание просроченной аренды (`sweepExpiredLeases`): без `effect_started_at` задание снова `queued`
  (считается попыткой — задание, которое роняет процесс, в итоге станет `failed`, а не зациклится);
  с `effect_started_at` — `needs_attention`, само оно больше не запустится.
- Ошибка обработчика: по умолчанию повтор с backoff 1, 2, 4… минут (не больше 30), после
  `max_attempts` — `failed`; если эффект начат — `needs_attention`. Обработчик может выбрать исход сам,
  бросив `JobError` с `outcome: 'retry' | 'fail' | 'needs_attention'` и `code`.
- Отмена (`cancelJob`) и перенос (`rescheduleJob`) атомарны: условие `status = ANY(...)` в том же UPDATE.
  Задание, которое воркер уже захватил, отменить нельзя.
- Старт — в `backend/src/index.js` после миграций и `moveQueue.resume()`; таймеры `unref`, старт не ждёт.
  По SIGTERM воркер первым делом перестаёт брать задания (флаг `stopping`; захват, который уже шёл,
  возвращается в очередь) и даёт текущим до 8 секунд, раньше закрытия HTTP-сервера.

## Гарантии

- **Не больше одного раза** — для вида, обработчик которого вызывает `ctx.markEffectStarted()` прямо перед
  необратимым шагом. Так устроен `send_message`: письмо никогда не уходит на сервер дважды. Если воркер
  умер посреди отправки или связь оборвалась без ответа сервера, задание `needs_attention`, автор получает
  уведомление и сам решает, отправить ли снова (и только явным действием).
- **Хотя бы один раз** — для всех остальных видов. Их обработчик обязан быть идемпотентным: после падения
  процесса задание выполнится ещё раз.

## Как добавить вид задания

1. Зарегистрировать обработчик при старте (рядом с `registerSendJobKind` в `index.js`):

   ```js
   registerJobKind('follow_up_reminder', {
     maxAttempts: 5,
     handler: async (job, ctx) => { /* job.payload, job.account_id, job.created_by */ },
     onSettled: (job) => { /* done, failed или needs_attention: уведомить автора */ },
   });
   ```

2. Ставить задания через `enqueueJob({ kind, payload, runAt | delayMs, createdBy, accountId, dedupeKey }, tx)`;
   `tx` — клиент транзакции, если вместе с заданием пишется что-то ещё.
3. Если шаг необратим (отправка, внешний API без идемпотентности) — вызвать `await ctx.markEffectStarted()`
   прямо перед ним. Записать результат вместе с завершением задания можно через `ctx.complete(async (tx) => …)`.
4. Содержимое (тексты, вложения) держать в своей таблице с `ON DELETE CASCADE` на `jobs`, не в `payload`.
5. Действия пользователя над заданиями писать в журнал (`services/auditLog.js`) без темы и тела.
6. Тесты — на PGlite с реальными миграциями (`services/testing/realSchema.js`), как
   `services/jobQueue.pglite.test.js` и `routes/send.queue.pglite.test.js`.

## Отправка через очередь

`POST /api/mail/send` проверяет и собирает письмо, пока автор ждёт (адреса, вложения, пересылаемые
вложения с IMAP, подпись, inline-картинки, пробная компиляция MIME), и ставит `send_message` на
`now + 5 с` или на выбранное `sendAt` (UTC, не в прошлом, не дальше года). Ответ — `{ jobId, sendAt,
scheduled }`. Идемпотентность — `X-Idempotency-Key` как `dedupe_key`; тот же ключ для отменённого письма или другого
времени — 409 (`send_cancelled`, `idempotency_conflict`). `sendAt` — ISO со смещением или `Z`. Ответ
несёт `dueInMs` по часам базы: клиент считает окно отмены от получения ответа, не смешивая часы.

Когда задание созрело, обработчик проверяет, что автор не отключён, и вызывает `deliverOutgoingMessage`:
Message-ID выбран при постановке, MIME компилируется в момент отправки (заголовок Date — время отправки),
дальше всё как раньше — журнал `message.sent` с настоящим Message-ID, контакты, копия в «Отправленных»,
Gmail threadId. Копия в «Отправленных» (APPEND до 20 секунд) делается уже вне слота воркера, автор
получает `send_done`, когда она готова. Если аренду сняли, пока сервер принимал письмо, задание всё равно
становится `done` (не `needs_attention`), чтобы повторная отправка не дала дубль. Если сервер принял
письмо, но отказал части получателей на RCPT (nodemailer в этом случае не падает, а отдаёт `info.rejected`),
задание всё равно `done`: отказанные адреса остаются в `payload.rejected` задания (их видят автор и
администраторы в `GET /scheduled/:id`), приходят автору в `send_done` (`rejected`) и записываются в статус
доставки письма (`message_delivery_status`, источник `submission`) как «не доставлено» с ответом сервера. Исход:

| Ситуация | Статус | Код |
|---|---|---|
| сервер принял письмо | `done` | — |
| 4xx, сервер недоступен, временный сбой OAuth, квота Gmail | повтор (до 5 попыток) | `smtp_temporary`, `smtp_connection_failed`, `oauth_refresh_failed`, `gmail_quota_exceeded` |
| 5xx, отказ аутентификации, нужен переподключ, отказ Gmail API | `failed` | `smtp_rejected`, `smtp_auth_failed`, `oauth_reconnect_required`, `gmail_*` |
| связь оборвалась после начала отправки, воркер умер | `needs_attention` | `send_uncertain`, `lease_expired` |
| автор отключён или удалён | `failed` | `author_disabled` (повторная отправка скрыта, остаётся «Изменить») |
| ящик удалён | `failed` | `account_missing` |

Управление — `/api/mail/scheduled`: список ожидающих и неотправленных писем ящика, отмена с возвратом
письма в редактор (`reason: undo | edit`) или без (`discard`), перенос и повторная отправка
(`resend: true`). Изменённое запланированное письмо возвращается со своим временем: редактор показывает
«Отправить <время>», а меню часов — «Отправить сейчас». Перенос делает письмо запланированным.
`scheduled_changed` рассылается только для запланированных и неотправленных писем, не для каждой отправки
с окном отмены; вкладки обновляют список с разбросом 1,5–3 секунды. Ящики общие: письмо в очереди видят все, у кого есть ящик (без Bcc), а меняют только
автор и администраторы. Журнал: `message.send_queued`, `message.send_cancelled`,
`message.send_rescheduled`, `message.send_failed`.

## Задания тенанта

Требование R-22 ([eop-panel-requirements.md](mail-node-research/eop-panel-requirements.md)) задумывало
отдельную таблицу `tenant_jobs` с одним исполнителем и блокировкой в БД. Этап 7a вместо неё использует эту
очередь: захват `SKIP LOCKED`, аренда, повторы, `failed` и перезапуск уже есть, и вторая таблица
повторила бы их. Отдельной миграции нет. Код — `backend/src/services/tenant/tenantJobs.js`, маршруты —
`backend/src/routes/mailNodeTenant.js`.

| Вид | Кто ставит | Что делает |
|---|---|---|
| `tenant_test_connection` | «Проверить подключение» (администратор) | сертификат исполнителя против отпечатка, токен Graph и `GET /domains`, EXO `whoami`; при удаче — и антиспам-политика |
| `tenant_poll` | таймер раз в 10 минут (`dedupe_key` — номер десятиминутного слота) и «Проверить сейчас» | сертификат (срок для оповещений) и `Get-BlockedConnector` (R-27); политика — если прочитана больше 6 часов назад или проверка подключения нашла, что в ней менять (тогда и запись, как у `tenant_antispam_read`) |
| `tenant_antispam_read` | «Проверить и исправить» | `Get-HostedContentFilterPolicy -Identity Default` (R-28) и, с раздела 5.14 требований, `MoveToJmf` для спама, явного спама, фишинга и массовой рассылки: запись только отличий и чтение снова; одна такая проверка за раз (блокировка `mail_node_antispam_run`) |
| `tenant_quarantine_release` (этап 7c) | таймер опроса (`dedupe_key` — слот, только если выпуск включён и прохода в очереди нет), «Выпустить сейчас», само задание (следующие 25 писем через 30 с) | выпуск явного фишинга, а с раздела 5.14 требований и обычного фишинга, спама, явного спама и массовой рассылки из карантина EOP в ящики узла (R-42; всё, кроме явного фишинга, — только при правиле «Спама» этой версии на узле), разделы 5.13 и 5.14 требований |
| `tenant_message_trace` (этап 7c) | «Спросить трассировку Microsoft» у отправленного письма (любой вошедший), само задание (продолжение списка или подробностей через 15 с) | трассировка письма по Message-ID (R-30) |
| `tenant_domain_sync` (этап 7b) | добавление, принятие и перезапуск домена, «Сделано» и «Готов», новый ящик в домене с зеркалом, «Выполнить шаги тенанта сейчас», таймер опроса (`dedupe_key` — домен и слот) и само задание (следующая пачка, повторный опрос `Get-AcceptedDomain`) | шаги тенанта домена (R-23 … R-26) и зеркало получателей DBEB (R-29), раздел 5.12 требований |

- Три вида этапа 7a идемпотентны (хотя бы один раз), `max_attempts` 1: опрос повторит следующий слот,
  проверку — кнопка. Ошибка шага не роняет задание: она пишется в результат с кодом. Проверка подключения
  только читает; `tenant_antispam_read` и опрос с раздела 5.14 требований пишут в политику Default, но
  только поля с другим значением и с чтением после записи, поэтому повтор безвреден; неудача записи
  остаётся в результате (`enforcement`) и поднимает оповещение `tenant_antispam_not_enforced`, повторит
  следующий шестичасовой опрос или кнопка.
- `tenant_domain_sync` пишет в тенант, но тоже идемпотентно: каждый прогон сначала читает, пишет только
  недостающее, ответ «не найден» на удаление считает выполненным, а «уже есть» на создание контакта —
  только после чтения, которое контакт показывает. `max_attempts` 6; троттлинг — `JobError` с `retry` и
  паузой из `Retry-After` (или 1, 2, 4 … минуты), сделанное до него сохраняется; запись, которая не прошла
  по другой причине, сразу не повторяется (её повторит слот опроса). Задание одно на домен в `queued`
  (повторная постановка возвращает его), и одновременно идёт один прогон домена: прогон захватывает строку
  домена атомарным `UPDATE` (`sync_lock_job`, захват старше 30 минут считается брошенным), а второй
  заканчивается как `done` без траты попытки и ставит новое задание через 30 с. Итог пишется в
  `mail_node_domains.tenant_sync` (миграция 0088), не в `integration_config`.
- `tenant_quarantine_release` выпускает письма из карантина (с раздела 5.14 требований включено по
  умолчанию, выключает администратор; выпускаются только типы `HighConfPhish`, `Phish`, `Spam`,
  `HighConfSpam`, `Bulk`, тип письма — в `quarantine_type`, миграция 0090; список проходится окном: первая
  страница и дальше от курсора `mail_node_phish_release_cursor`; каждый проход читает правило «Спама» на
  узле, и пока оно не этой версии, всё, кроме явного фишинга, ждёт без записи в таблицу):
  строка `tenant_quarantine_releases` (миграция 0089) — захват и идемпотентность. Одновременно идёт один
  проход: блокировка в `integration_config` `mail_node_phish_release_run` (старше 30 минут — от умершего
  прохода), второе задание (слот и кнопка в один момент, истёкшая аренда) заканчивается сразу. Перед
  выпуском письмо читается по `Identity`, выключатель читается снова, строка атомарно становится
  `releasing` (захват другого прохода моложе 10 минут не перехватывается), выпуск и запись `released` с
  журналом `tenant.quarantine_released` — в одной транзакции, журнал только при настоящем переходе в
  `released`; оставшаяся `releasing` на следующем проходе сначала читается снова (выпущено — отмечается,
  нет — выпуск повторяется, не больше трёх попыток; неудачное чтение тоже попытка). Продолжение через
  30 с — только если проход что-то изменил. `max_attempts` 4; троттлинг — `JobError` с `retry` и паузой,
  попытка письму не засчитывается.
- `tenant_message_trace` хранит итог в `message_eop_traces` (миграция 0089, 45 дней), а не в
  `integration_config`; строка и задание пишутся в одной транзакции. Своё ведро в 20 запросов Graph на 5
  минут (80 — у прохода R-43), задание резервирует запросы до первого и возвращает неиспользованное:
  без запросов задание заканчивается и ставит новое на момент, когда ведро наполнится (`trace_budget`,
  попытка не тратится); троттлинг Graph — повтор через минуту; недочитанный список или подробности —
  новое задание с курсором. `max_attempts` 6; если повторы кончились, `onSettled` пишет в строку `failed`
  с кодом задания.
- Результат пишется в `integration_config` `mail_node_tenant_state` вместе с завершением задания
  (`ctx.complete`); payload пустой, токенов и ассерций в строках нет.
- Виды регистрируются при старте всегда, даже без исполнителя тенанта: задание, оставшееся в очереди,
  падает сразу с `tenant_driver_missing` или `tenant_not_configured`, а не ждёт.
- Кнопка, нажатая, пока задание её вида в `queued` или `running`, возвращает это задание, нового не ставит.
- Готовые задания хранятся, как все, 7 дней: опрос даёт до ~1000 строк `done`, их удаляет обычная чистка.
- Одновременность (R-38): воркер очереди берёт до 4 заданий, поэтому ExoRunner в backend пропускает к
  исполнителю одну операцию EXO за раз, исполнитель тоже держит одну; Graph — не больше 4 запросов.
