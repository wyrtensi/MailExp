# Служба узла: обновление всего по кнопке и бэкап почты из панели

> Статус: дизайн от 2026-10-06, согласован с владельцем в переписке. Меняет прежнее решение
> «mailcow обновляется отдельно от панели» ([deployment-system.md, разделы 5 и 6](../../architecture/deployment-system.md)).
> Реализация — четыре PR (A-D), раздел «Разбивка».

## Зачем

Кнопка «Обновить» в панели обновляет только панель. Почтовый узел (mailcow и скрипты хоста узла)
обновляется руками по SSH: `git checkout` того же коммита, `setup.sh`, отдельно `./update.sh` mailcow.
Бэкап узла (`node-backup.sh`) идёт ночью, но из панели его не запустить и не увидеть его состояние.

Владелец хочет:

1. Одна кнопка «Обновить» обновляет всё: панель, скрипты узла и, когда новый выпуск этого требует,
   mailcow. Панель сама знает, нужно ли обновлять mailcow.
2. Данные не теряются: перед изменением узла — его бэкап; старые бэкапы чистятся автоматически.
3. В панели — «Бэкап почты сейчас» и состояние последнего бэкапа узла. Состав бэкапа узла не
   меняется: вся почта (vmail), база mailcow (домены, ящики, алиасы), ключи mail_crypt, конфигурация.
4. Код mailcow не меняется.

## Принятые решения

- **Канал панель ↔ узел — HTTPS по токену, узел ходит к панели.** API mailcow не умеет команд хоста,
  а менять mailcow нельзя, поэтому на узле своя служба. Она сама обращается к панели (long poll),
  на узле не открывается новых портов, в nginx mailcow ничего не добавляется. Отвергнуто: SSH из
  панели (ключ панели давал бы shell на почтовом сервере), HTTPS-агент на узле со своим портом
  (ещё одна точка входа с правами root).
- **Версия mailcow закреплена в выпуске MailExpert.** Файл `deploy/mailcow-version` хранит проверенную
  на стенде версию mailcow. Кнопка доводит узел ровно до неё; совпадает — mailcow не трогается.
  Непроверенный mailcow на узел не попадает.
- **Откат mailcow вниз не делается.** У mailcow миграции базы, штатного отката версии нет. Сбой
  обновления mailcow останавливает задание; панель предлагает повторить или восстановить узел из
  снимка `pre-update` (`node-restore.sh`) после явного подтверждения.

## Устройство

### Служба узла `mailexpert-node-agent`

- Ставится `setup.sh` на узле (systemd-юнит; на хосте без systemd — cron, как остальные таймеры узла),
  копируется в `/opt/mailexpert-node` вместе с другими скриптами. Работает от root (docker, файлы mailcow).
- Цикл: `GET https://<PANEL_HOST>/api/node-agent/next` с токеном, ожидание до 50 с; получив задание,
  выполняет его и шлёт `POST /api/node-agent/jobs/<id>` со статусом, шагом и хвостом лога (без секретов).
- Задания — фиксированный список, параметры проверяются на узле:
  - `status` — версия скриптов (коммит), версия mailcow, контейнеры, `node-backup.sh --status`;
  - `backup` — `node-backup.sh --tag manual` (кнопка) или `--tag pre-update` (перед обновлением);
  - `update <sha>` — раздел «Обновление».
- **Защита от взломанной панели:** коммит `<sha>` служба скачивает сама из официального репозитория
  (`git fetch` в `/opt/mailexpert-node-src`) и выполняет только коммит, входящий в историю `origin/main`.
  Панель может выбрать версию из истории, но не подсунуть свой код. Версию mailcow служба берёт из
  `deploy/mailcow-version` этого коммита, а не из ответа панели.
- Токен: «Подключить службу узла» в разделе «Почтовый узел» показывает его один раз вместе с командой
  `setup.sh --panel-url https://<PANEL_HOST> --agent-token-file <файл>`; в базе панели — только хеш;
  перевыпуск отзывает старый. Токен на узле — файл `0600` в `/etc/mailexpert-node/`.
- Панель за Cloudflare Access: служба добавляет заголовки service token Access (`CF-Access-Client-Id`,
  `CF-Access-Client-Secret`) из того же файла настроек; ссылка — в [cloudflare.md](../../operations/cloudflare.md).

### Обновление по кнопке

1. Панель обновляется как сейчас (`updater.sh` → `update.sh`, бэкап, автооткат).
2. Новая панель после проверки готовности ставит узлу задание `update <sha>` (если служба узла подключена;
   нет — показывает прежний шаг `next:` «на узле — тот же коммит и `setup.sh`»).
3. Служба узла:
   1. `node-backup.sh --tag pre-update`; не удался — стоп, узел не тронут;
   2. checkout `<sha>` в `/opt/mailexpert-node-src`, `setup.sh` без параметров; сбой — checkout
      прежнего коммита и `setup.sh`, задание `failed`;
   3. если `deploy/mailcow-version` отличается от версии на узле — обновление mailcow до неё штатными
      средствами mailcow (способ закрепить версию без правки mailcow — исследование PR D; если его нет,
      PR D останавливается и вопрос уходит владельцу), затем `setup.sh` и, если он изменил
      `mailcow.conf`, `docker compose down && up -d`;
   4. проверки: контейнеры mailcow, `eop-ranges.sh` (файрвол и порты), API mailcow отвечает панели;
   5. удаление образов mailcow, которые больше не используются.
4. Панель показывает одно обновление с частями «панель» и «узел» и журналом шагов.

**Простой почты.** EOP держит входящие письма не дольше 24 часов и повторяет доставку каждые 15 минут
([mail-node.md, раздел 6д](../../operations/mail-node.md)). Обновление mailcow останавливает приём на
минуты; панель предупреждает об этом перед запуском и не начинает часть mailcow, если узел уже недоступен.

### Бэкап почты из панели

- Раздел «Почтовый узел»: последний бэкап (время, размер, успех, проверка по воскресеньям) из задания
  `status`; кнопка «Бэкап почты сейчас» ставит задание `backup`.
- Хранение: как сейчас (7 ежедневных, 4 недельных, 6 месячных, снимки переезда); снимки `pre-update`
  узла — 5 последних, как у панели.

## Проверка

- backend: токен (хеш, отзыв), очередь заданий узла, long poll, права (только админ ставит задания,
  только служба с токеном их забирает) — vitest и PGlite;
- скрипты узла: bats (проверка коммита в `origin/main`, откат скриптов, разбор заданий), shellcheck;
- стенд: служба узла в me-stage (cron-вариант), кнопка бэкапа и обновление по кнопке, включая mailcow.
